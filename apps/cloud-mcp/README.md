# Rox Cloud MCP

MCP-сервер для Rox Cloud: любой клиент MCP (Claude Code, OMP, Cursor, свой агент) получает
возможность создавать машины, выполнять команды, читать и писать файлы, перечислять и
останавливать машины — с одним ключом Rox.

Сервер разговаривает только с HTTP API Rox Cloud (`apps/cloud-api`). Ключей провайдеров
(Daytona, Modal и других) у него нет и быть не может: их держит сервис Rox Cloud.

## Что нужно

- `bun` 1.2 или новее.
- Ключ Rox вида `rox_sk_…` с правами `sandboxes:read` и `sandboxes:write`.
- Запущенный Rox Cloud API. Локально это `apps/cloud-api` на `http://localhost:8787`.

Зависимостей нет: только стандартная библиотека и `bun`.

## Запуск

```sh
export ROX_API_KEY=rox_sk_...
export ROX_CLOUD_API_URL=http://localhost:8787   # по умолчанию именно этот адрес
cd apps/cloud-mcp
bun run src/index.ts
```

Оба значения читаются только из окружения. Если `ROX_API_KEY` не задан, сервер пишет
объяснение в stderr и завершается с кодом 1.

Подключение в клиенте MCP:

```json
{
  "mcpServers": {
    "rox-cloud": {
      "command": "bun",
      "args": ["run", "/полный/путь/apps/cloud-mcp/src/index.ts"],
      "env": {
        "ROX_API_KEY": "rox_sk_...",
        "ROX_CLOUD_API_URL": "http://localhost:8787"
      }
    }
  }
}
```

## Инструменты

| Имя | Аргументы | Что делает |
| --- | --- | --- |
| `create_sandbox` | `os?`, `cpu?`, `memoryGb?`, `ttlSec?`, `provider?` | Создаёт машину. По умолчанию `linux`, 2 ядра, 4 ГБ. |
| `exec` | `sandboxId`, `command`, `timeoutSec?` | Выполняет команду, возвращает `stdout`, `stderr`, `exit_code`. |
| `read_file` | `sandboxId`, `path` | Читает файл как UTF-8; для двоичного файла добавляет предупреждение. |
| `write_file` | `sandboxId`, `path`, `content` | Пишет текст в UTF-8, заменяя файл целиком. |
| `list_sandboxes` | — | Перечисляет машины ключа. |
| `stop_sandbox` | `sandboxId` | Останавливает машину, не удаляя её. |

Ответ инструмента — один текстовый блок. Успех — данные в JSON (у `read_file` — сам текст
файла). Отказ Rox Cloud — тот же блок с `isError: true` и полями `code`, `message`,
`request_id`, `status`. Неизвестный инструмент и неверные аргументы — ошибка протокола
`-32602`, а не результат инструмента.

Ненулевой код выхода команды — это ответ команды (`exit_code`), а не ошибка вызова: агент
сам решает, что с ним делать.

## Протокол

- Транспорт: построчный JSON-RPC 2.0 по stdin/stdout (одно сообщение — одна строка).
- Поддерживаются `initialize` (версия протокола `2025-06-18`, `tools: {}`, `serverInfo.name = rox-cloud`),
  `notifications/initialized`, `tools/list`, `tools/call`, `ping`.
- Уведомления (сообщения без `id`) ответа не получают.
- Неизвестный метод — `-32601`, сломанный JSON — `-32700`, неверные параметры — `-32602`,
  внутренний сбой — `-32603`.
- В stdout уходят только ответы протокола. Диагностика — в stderr, поэтому клиент не ломается
  от служебных сообщений.

## Что важно знать о контракте API

- `POST /v1/sandboxes` требует заголовок `Idempotency-Key`. Сервер генерирует его
  (`crypto.randomUUID()`), поэтому повторный вызов того же инструмента создаёт новую машину;
  ключ идемпотентности можно задать явно через `createSandbox(..., { idempotencyKey })` в коде.
- API требует `os`, `cpu`, `memoryGb` в теле создания. В схеме инструмента они необязательны,
  потому что сервер подставляет значения по умолчанию до вызова API.
- Файлы передаются сырыми байтами: `GET /files?path=…` возвращает `application/octet-stream`,
  `PUT /files?path=…` принимает тело запроса и отвечает `204 No Content`.
- `DELETE /v1/sandboxes/{id}` в инструменты не выведен: остановка (`stop_sandbox`) обратима,
  удаление — нет. Метод есть в клиенте (`deleteSandbox`) для кода, который осознанно его зовёт.

## Безопасность

- Ключ Rox читается только из `ROX_API_KEY` и уходит только в заголовок `Authorization`.
- Ключ не попадает ни в один текст ответа: клиент вырезает его из сообщений об ошибках,
  подставляя `***`.
- Сервер ничего не пишет в файлы и не хранит состояние между запросами.

```sh
cd apps/cloud-mcp

```
