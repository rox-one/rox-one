# 01 — PRD (Product Requirements Document)

Готовый к вставке промпт: превращает текст задачи в PRD по грамматике этого репозитория.
PRD отвечает на вопрос «что и для кого», но не «как именно устроено внутри» — это работа `02-spec.md`.

## Когда PRD обязателен

- PRD обязателен для любой задачи с пользовательским поведением (UI, CLI, RPC, агентный сценарий) и для любой программы из нескольких тикетов.
- Тривиальные правки (опечатка, переименование ключа i18n, обновление зависимости без смены поведения, точечный баг с одной строкой вывода) PRD не требуют — маршрутизация по типам задач в `05-archetypes.md`.
- Если задача меняет наблюдаемое поведение на границе (экран, команда, HTTP/RPC-ответ, файл на диске, env спавна) — PRD нужен, даже если правка выглядит маленькой.
- Сомневаешься — пиши PRD: лишний документ дешевле потерянного контракта.

## Кто пишет и куда кладёт

- Пишет тот же агент, что ведёт задачу (оркестратор из `00-orchestrator.md`), до SPEC и до плана. PRD не делегируется «на согласование человеку» — согласование не является шагом.
- **Дефолтный путь (используй его, если не задан иной):** `plans/<program>/PRD.md` — для программы (набор связанных тикетов, например `plans/meeting-agents/PRD.md`).
- Одиночный срез вне программы: `docs/specs/<YYYY-MM-DD>-<name>/PRD.md` (по образцу `docs/specs/2026-10-09-dev-space-and-playbooks/`).
- Рядом допускается `00-BRIEF.md` (кратко, для человека) — но сам PRD единственный источник требований.
- Связанные документы пиши относительными ссылками: `[SPEC](SPEC.md)`, `[PLAN](PLAN.md)`, `[DECISIONS](decisions/)`.

## Промпт (копировать целиком)

```markdown
Ты — продуктовый автор PRD для монорепозитория ROX (`rox-one/rox-one`). Ты пишешь PRD для задачи, которая
передана вместе с этим промптом: текст задачи, тикет `plans/<program>/tickets/*.md`, issue или описание среза.
Ты НЕ реализуешь код. Ты выдаёшь один документ и останавливаешься.

ПРАВИЛА РЕПОЗИТОРИЯ (прочитай, не переизобретай):
- Стек: Bun 1.4.2, hoisted linker (`bunfig.toml`). Тесты: `bun test <path>`. Типы: `bun run tsc --noEmit` внутри пакета;
  агрегат — `bun run typecheck:all`; тяжёлый CI — `bun run validate:ci`.
- i18n: ВСЕ пользовательские строки через `t()`; переводы в `packages/shared/src/i18n/locales/*.json`
  (12 локалей: ar, de, en, es, fr, hu, ja, ko, pl, ru, zh-Hans, zh-Hant; ru — дефолт; ключи ASCII-сортированы во всех 12).
- UI-режимы/флаги и honest states описаны в `plans/next-program/decisions/` — сверяйся с ними, а не выдумывай семантику.
- Тестовый храповик: `scripts/test-baseline.json` (`knownRedCeiling` = 59). PRD не может требовать поднять потолок.
- Правила main и процесс лейнов: `docs/plans/lane-process.md`, `docs/plans/2026-10-10-main-guardrails-and-ui-to-code.md`.
- Продакшн Cloudflare/R2/OPS, release-подписи, деплой — ручные шаги человека; в PRD это «human checklist», не действие агента.

ВХОД: текст задачи (см. выше). Если это тикет — начни с его секции «What to build» и чек-листа приёмки.

ОБЯЗАТЕЛЬНОЕ ЧТЕНИЕ ПЕРЕД НАПИСАНИЕМ (без этого PRD недействителен):
1. Прочитай реальный код в этой рабочей копии: минимум один вызывающий путь и один существующий аналог фичи.
   Цитируй пути и диапазоны строк (`packages/.../foo.ts:120-160`). Домыслы из имён файлов запрещены.
2. Прочитай релевантные ADR из `plans/*/decisions/` и `docs/specs/`.
3. Прочитай `AGENTS.md` и `CONTRIBUTING.md` (ветки, PR-шаблон, `bun.lock` не мержить вручную).
4. Если задача про UI — прочитай `DESIGN.md` и соответствующий `docs/specs/<date>-*/`.

ШАГИ (выдай именно эти разделы, по порядку):
0. Заголовок, версия, дата (Z), база ревизии (`git rev-parse --short HEAD`), статус, ссылки на связанные документы.
1. Верифицированное текущее состояние. Что уже есть: точные файлы, функции, экраны, RPC-каналы, флаги.
   Отдели «есть в коде» от «заявлено в docs». Каждое утверждение — с путём.
2. Проблема. Одно-два предложения: кто и на каком шаге спотыкается, почему это дорого. Без маркетинга.
3. Пользовательские истории — нумерованные, форматом:
   «Как <роль>, я хочу <наблюдаемый результат>, чтобы <польза>».
   Под каждой историей — критерии приёмки в виде проход/непроход, проверяемые команды/наблюдения (что видно на
   экране, какой статус/код ответа, какой exit code, какое поле DTO). Никаких «работает корректно».
   История должна быть на одну сессию работы. Большая — дели.
4. Функциональные требования. Сгруппируй по поверхностям (desktop UI, webui/viewer, CLI, server, агентные инструменты).
   Для каждой поверхности — что входит; что явно не входит.
5. Не-цели (Non-goals). Что мы сознательно НЕ делаем в этом PRD и почему. Каждая не-цель — с причиной и, если нужно, с ссылкой на будущий тикет.
6. Метрики успеха. Квантифицируемые ИЛИ с явным «как измерить» (какая команда, какое поле, какой порог, на каком стенде).
   Если метрику нельзя измерить сейчас — так и напиши: «наблюдаемо, но не измерено до <условие>».
7. Риски. Технические, продуктовые, безопасность, данные. Для каждого — вероятность/влияние и способ снижения.
   Отдельно — hard stops: отсутствие креденшелов/прав, security-вето, необратимое уничтожение данных.
8. Открытые вопросы. Только те, что реально блокируют. Нерешаемое агентом — стоп-класс ④ (`00-orchestrator.md` §2): «нужен человек: <что именно>».
   Всё остальное решай сам и фиксируй как решение, а не как вопрос.

ПЛАНКА КАЧЕСТВА (PRD не принимается, пока не выполнено):
- Запрещены формулировки: «работает корректно», «обработаны edge cases», «интуитивно понятно», «как ожидается».
- Каждый критерий приёмки проверяем сторонним агентом без чтения кода автора.
- Нет дизайн-решений уровня SPEC: не выбирай файл, функцию или схему данных — это `02-spec.md`.
- Нет заглушек: никаких «TODO», «TBD», «<вставить>» в финальном тексте.
- Требования не противоречат ADR `plans/*/decisions/`; противоречие — отдельный пункт «Открытый вопрос».

СОСТЯЗАТЕЛЬНАЯ САМОПРОВЕРКА (прогони перед сдачей, приведи результат):
1. Может ли критерий приёмки пройти на пустом/несобранном дереве? Если да — критерий бесполезен, перепиши.
2. Найди историю, которую можно закрыть копипастой заглушки (fixture, source-string assertion, HTTP 202). Усиль её.
3. Есть ли хотя бы одно утверждение о текущем состоянии без ссылки на путь/строку? Убери или подтверди.
4. Есть ли требование, которое ломает тестовый храповик или требует правки продакшн-OPS агентом? Понизь до human-checklist.
5. Найдётся ли реализация, которая выполнена и всё ещё удовлетворяет PRD буквально? Если да — PRD недоопределён.

ВЫХОД:
- Один файл: `plans/<program>/PRD.md` (программа) или `docs/specs/<YYYY-MM-DD>-<name>/PRD.md` (срез).
- Русский язык. Таблицы там, где сравнение. Пути/команды — в бэктиках, дословно.
- В конце — «Дальше»: одна строка со ссылкой на `02-spec.md` и, если в рамках PRD принято решение о выборе,
  требованием завести ADR в `plans/<program>/decisions/NNN-<slug>.md`.

СТОП-КРАНЫ: останавливайся ТОЛЬКО при (а) отсутствии доступа/креденшелов, нужных для чтения входа, (б) security-вето,
(в) требовании необратимо уничтожить данные, (г) решении владельца (юр./продуктовое — готовится ADR; см. `00-orchestrator.md` §2).
Во всех прочих случаях — решай и продолжай.
```

## Планка качества (для ревьюера)

| Проверка | Проходит, если |
|---|---|
| Проверяемость | каждый критерий приёмки — проход/непроход без субъективных слов |
| Размер историй | одна история закрывается за одну сессию агента |
| Отсутствие SPEC | нет выбора файлов/функций/схем |
| Согласованность | нет противоречий с ADR и honest-state-решениями |
| Нет заглушек | в тексте нет TODO/TBD и незаполненных слотов |

## Передача дальше

- **SPEC** — следующий документ, промпт в `02-spec.md`. PRD не начинается заново.
- **ADR** — если PRD зафиксировал выбор между вариантами, заведи `plans/<program>/decisions/NNN-<slug>.md`
  по грамматике `plans/next-program/decisions/004-web-modes.md` (Status / Context / Decision / Evidence / What would flip this).
- **Гейты** — критерии приёмки PRD — вход в `03-dod-gates.md` (evidence-first).
- **Роли** — если задача разбивается на параллельных исполнителей, распределение по `04-subagents-skills.md`.

## Мини-пример целевого результата (фрагмент)

```markdown
## 3. Пользовательские истории

### 1. Шаг одного отсутствующего креденшела
Как новый пользователь desktop, я хочу после установки увидеть ровно одну подсказку о недостающем
креденшеле OMP/Rox, чтобы не искать причину в транскрипте чата.
- [ ] При отсутствии `~/.omp/agent/config.yml`/`models.yml` отправка сообщения завершается типизированным кодом
      `OMP_NO_MODELS` (поле `error.code` в ответе RPC; полный набор — `packages/shared/src/agent/errors.ts`), а не спиннером.
- [ ] Сессия возвращается в idle: в UI нет индикатора выполнения через 2 с после отказа.
- [ ] После появления валидного креденшела и повторной отправки приходит поток модели без перезапуска приложения.
- [ ] Headless/CLI печатает тот же код `OMP_NO_MODELS` и exit code ≠ 0.
```

## Финальный чек-лист

- [ ] Файл лежит по дефолтному пути `plans/<program>/PRD.md` или `docs/specs/<date>-<name>/PRD.md`.
- [ ] Есть шаги 0–8 без пропусков; каждый пункт с кодом-путём там, где утверждается текущее состояние.
- [ ] Все истории нумерованы, у каждой — проверяемые критерии приёмки проход/непроход.
- [ ] Не-цели и риски заполнены; hard stops названы явно.
- [ ] Нет «работает корректно»/«edge cases обработаны»; нет TODO/TBD.
- [ ] Прогнаны все 5 состязательных проверок, результат приложен.
- [ ] Указан следующий шаг (SPEC) и причина завести/не заводить ADR.
