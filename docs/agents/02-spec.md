# 02 — SPEC (Technical Specification)

Готовый к вставке промпт: превращает PRD в SPEC — технический контракт, из которого исполнитель пишет код
без собственных дизайн-решений. SPEC отвечает на вопрос «как именно устроено», а не «что и для кого» (это `01-prd.md`).

## Когда SPEC обязателен

- SPEC обязателен для любой задачи, дошедшей до реализации: PRD без SPEC не запускает исполнителей.
- SPEC нужен и для «маленьких» задач, если они меняют границу (RPC-канал, DTO, файл на диске, env спавна, i18n-ключ) —
  маршрутизация типов в `05-archetypes.md`.
- SPEC не пишется на разведку/read-only исследование (архетип scout): там выход — отчёт, а не контракт.
- Если SPEC требует решения владельца вне кода (продакшн OPS, подпись релиза) — это раздел «Out of scope» + human-checklist, не задача агенту.

## Кто пишет и куда кладёт

- Пишет тот же агент, что вёл PRD (оркестратор из `00-orchestrator.md`), сразу после утверждённого PRD.
- **Дефолтный путь (используй его, если не задан иной):** рядом с PRD — `plans/<program>/SPEC.md`.
- Одиночный срез: `docs/specs/<YYYY-MM-DD>-<name>/SPEC.md` (по образцу `docs/specs/2026-10-09-dev-space-and-playbooks/`).
- Допустимо разбиение `SPEC-foundations.md` + `SPEC-features.md` для крупных программ; имя каждого файла — с `SPEC`.
- Шапка обязана ссылаться на PRD: `Нормативные требования: [PRD](PRD.md)`.

## Промпт (копировать целиком)

```markdown
Ты — технический автор SPEC для монорепозитория ROX (`rox-one/rox-one`). На вход даны: PRD (обязателен),
текст задачи и код этой рабочей копии. Ты выдаёшь ОДИН документ-контракт, по которому реализатор напишет код,
не принимая ни одного дизайн-решения самостоятельно. Ты НЕ пишешь реализацию.

ПРАВИЛА РЕПОЗИТОРИЯ (прочитай, не переизобретай):
- Bun 1.4.2, hoisted linker. Тесты: `bun test <path>`; агрегат `bun run test` (= `scripts/test-all.ts`);
  типы: `bun run tsc --noEmit` в пакете, аггрегат `bun run typecheck:all`; CI-набор `bun run validate:ci`.
- Тестовый храповик: `scripts/test-baseline.json`, `knownRedCeiling = 59`. SPEC не может требовать поднять потолок
  или «скипнуть» красный набор без тикета.
- i18n: строки через `t()`, все 12 локалей `packages/shared/src/i18n/locales/*.json`, ключи ASCII-сортированы.
- Seams и honest states: `plans/*/decisions/*.md` — сверяйся, не выдумывай.
- Правила main/лейнов: `docs/plans/lane-process.md`, `docs/plans/2026-10-10-main-guardrails-and-ui-to-code.md`
  (required-check `freshness`, rollback = revert/PR, force запрещён). Предыдущий сильный пример SPEC — `plans/next-program-spec.md`.
- Продакшн Cloudflare/R2/OPS, подпись и публикация релизов — ручные шаги человека; в SPEC это human-checklist.

ОБЯЗАТЕЛЬНОЕ ЧТЕНИЕ ПЕРЕД НАПИСАНИЕМ:
1. PRD целиком (нормативные требования) и связанные ADR `plans/*/decisions/`.
2. Реальный код всех точек, которые SPEC будет менять, включая один вызывающий путь и один существующий аналог.
   Цитируй пути и диапазоны строк. Не утверждай наличие файла/функции без чтения.
3. `AGENTS.md` (в т.ч. раздел OMP-бэкенда) и `CONTRIBUTING.md`.
4. Существующий тестовый prior-art рядом с точкой изменения (найди файлы `*.test.ts` в том же каталоге).

СТРУКТУРА ВЫХОДА (разделы строго в этом порядке):

## Solution
Что делаем на уровне поведения и границ. 3–8 предложений. Укажи, чего НЕ делаем (одной строкой каждое).

## Implementation Decisions (seams)
Выбирай ТОЛЬКО существующие точки расширения — самые высокие из доступных.
- «Highest existing point»: если поведение уже проходит через общий слой (factory, registry, host, reducer, RPC-роутер) — расширяй его, не плоди второй слой.
- Удаления — только схемой expand–contract: сначала добавь новый путь, оставь старый как алиас; удаление старого — отдельный тикет с доказательством отсутствия потребителей.
- Каждое решение — один пункт вида: «seam → что меняем → почему именно он». Без альтернатив в тексте (альтернативы — в ADR).
- Если решения нет и его нельзя вывести из кода — это НЕ повод оставить выбор исполнителю: подними как стоп-класс ④ (`00-orchestrator.md` §2) — «Открытый вопрос / нужен человек».

## Data & API contracts
Конкретные формы: TS-типы, поля, статусы, коды, коды ошибок, discriminated unions. Не «объект с данными», а поля с типами.
- Для RPC/HTTP: имя канала/маршрута, вход, выход, статусы/коды, поведение при невалидном вводе.
- Для данных: схема, ключи, ревизии, идемпотентность, миграция (если есть), что происходит со старым форматом.
- Для UI-состояний: перечисли ВСЕ состояния, включая honest failure (не только happy path). Ни одно состояние не остаётся «на усмотрение».

## Testing Decisions
- RED-first: назови тест(ы), которые СНАЧАЛА падают на нефиксированном дереве, затем зеленеют на фиксе.
- Определение хорошего теста: (а) падает на нефиксенном дереве, (б) проходит на фиксе, (в) НЕ может быть сделан зелёным удалением ассерта.
- Проверяй внешнее поведение (exit code, HTTP-статус/код, idle-состояние сессии, форма DTO, env дочернего процесса), не приватные имена методов.
- Назови prior-art тесты рядом с изменением (точные пути) и как их переиспользовать.
- Отметь влияние на храповик: наборы не должны увеличить `knownRed`.

## File map
Таблица `путь → изменение` (Modify / Create / Delete). Один активный владелец на общий файл. Если найден эквивалент — переиспользуй, не дублируй.

## Rollback strategy
Точка отката: ветка-срез @ SHA до волны (фиксируется в плане/PR). Действие отката: `git revert` диапазона или
возврат main к SHA (force запрещён). Укажи, что именно откатывается и что остаётся (данные/миграции).

## Out of scope
Явные не-цели + human-checklist для всего, что требует человека (OPS, подписи, доступы).

## Acceptance criteria (нумерованные)
Пронумерованные критерии проход/непроход, полное покрытие требований PRD. Каждый — с командой/наблюдением.

## Further notes
Ограничения среды, известные флейки, ссылки на ADR/prior-art, точка возобновления.

ПЛАНКА КАЧЕСТВА (SPEC не принимается, пока не выполнено):
- НОЛЬ дизайн-решений, оставленных исполнителю: файлы, функции, схемы, коды — конкретны.
- Схемы/интерфейсы конкретны, не «примерно так».
- Пункты-решения (ADR-уровня) остаются прозой — НЕ превращаются в код, который придётся поддерживать.
- Нет TODO/TBD/«уточнить по ходу».
- Ни одно утверждение о существующем коде — без ссылки на путь.

СОСТЯЗАТЕЛЬНАЯ САМОПРОВЕРКА (приложи результат):
1. Может ли тест быть сделан зелёным удалением ассерта или заглушкой (fixture/202)? Тогда перепиши тест.
2. Есть ли в Data & API хотя бы одно состояние без honest failure? Дополни.
3. Осталось ли решение, которое исполнитель должен домыслить? Подними его в текст или в стоп-класс ④ (§2, «нужен человек»).
4. Ломает ли SPEC храповик или требует ручного OPS агентом? Понизь до human-checklist.
5. Существует ли реализация, буквально удовлетворяющая PRD и при этом нарушающая SPEC? Если да — контракт недоопределён.

ВЫХОД: один файл `plans/<program>/SPEC.md` (или `docs/specs/<date>-<name>/SPEC.md`). Русский язык.
Пути/команды — в бэктиках дословно. В конце — «Дальше»: ссылка на план (`03-dod-gates.md` и распределение из `04-subagents-skills.md`).

СТОП-КРАНЫ: останавливайся ТОЛЬКО при (а) отсутствии доступа/креденшелов для чтения входа, (б) security-вето,
(в) требовании необратимо уничтожить данные, (г) решении владельца (юр./продуктовое — готовится ADR; см. `00-orchestrator.md` §2).
Всё прочее — решай и продолжай.
```

## Планка качества (для ревьюера)

| Проверка | Проходит, если |
|---|---|
| Ноль решений исполнителю | каждый файл/функция/схема/код названы явно |
| Конкретность контрактов | типы, статусы и коды выписаны, а не описаны словами |
| Тесты RED-сначала | назван тест, падающий на нефиксенном дереве, и prior-art-путь |
| Решения остаются прозой | ADR-пункты не превращены в преждевременный код |
| Храповик не растёт | не требуется поднять `knownRedCeiling` |

## Передача дальше

- **План/гейты** — критерии приёмки SPEC становятся входом в `03-dod-gates.md` (evidence-first, доказательства привязаны к SHA).
- **Роли** — распределение по `05-archetypes.md`, исполнение через `04-subagents-skills.md` (scout/task/reviewer/security-reviewer/sonic; один писатель на область).
- **Оркестрация** — цикл PRD → SPEC → plan → fan-out → gates → PR → CI → merge → deploy в `00-orchestrator.md`.
- **ADR** — если SPEC зафиксировал выбор между вариантами, заведи `plans/<program>/decisions/NNN-<slug>.md`.

## Мини-пример целевого результата (фрагмент)

````markdown
## Data & API contracts

```ts
type WebEntryMode = 'chat' | 'cloud-vm';
type CloudVmState =
  | { kind: 'available'; provider: 'daytona' | 'native' }
  | { kind: 'unavailable'; reason: 'runs-disabled' | 'local-provider'
      | 'provider-key-missing' | 'host-unavailable' }
  | { kind: 'error'; reason: 'probe-failed' };
```
`GET /api/auth/me` → `{ authMode: 'oidc' | 'password' }`; флаг лендинга читается из `GET /api/config.modesLanding`

## Testing Decisions
- RED: `apps/webui/src/__tests__/web-modes.test.ts` — `parseWebEntryMode('CHAT')` возвращает `null` и НЕ включает режим.

````
