# 05 — Архетипы задач: дельты гейтов и DoD

Документ отвечает на вопрос «как меняется цикл задачи, если это не Feature». Базовый
цикл и гейты `G0–G7` определены в [`03-dod-gates.md`](./03-dod-gates.md);
здесь — только **дельты**. Команды каждого гейта — в [`06-runbook.md`](./06-runbook.md).

**Канон гейтов — из [`03-dod-gates.md`](./03-dod-gates.md) (при расхождении верен `03`):**

| Гейт | Имя | Смысл |
|---|---|---|
| G0 | Recon | база SHA, область, ownership, точка отката; BLOCKED-проба (секреты/права/данные) |
| G1 | Типы и сборка | `bun run typecheck:all` / per-package `tsc --noEmit`, точечные сборки |
| G2 | Тесты и i18n | затронутые наборы + храповик `bun run test`; 12 локалей |
| G3 | Ревью | независимый `code-review` субагент |
| G4 | Security | `security-reviewer` (право veto) |
| G5 | Smoke | живой прогон изменённой поверхности (скриншот + SHA) |
| G6 | Ship | `gh pr create` → `freshness` strict → merge |
| G7 | Деплой + Live | деплой пайплайном → живой smoke |

Общее правило: **гейт не пропускается, а переопределяется**. Если архетип снимает гейт —
это явно записано ниже; «нет изменений» не значит «нет доказательства».

---

## 1. Feature (вертикальный срез)

**Когда.** Новое пользовательское поведение или расширение контракта; один тикет = один
вертикальный срез (UI → IPC/RPC → backend), а не «весь домен».

**Фазовые дельты.** Полный цикл PRD → SPEC → plan → fan-out → gates. Волны как в
`plans/next-program-prompt.md`: WAVE 0 prefactor (если нужен шов), WAVE 1 — параллельные
срезы, WAVE 2 — зависимые, WAVE 3 — reviewers + live E2E.

**Гейт-дельты vs G0–G7.** База без исключений.
- SPEC: обязателен контракт «действие в UI → реальный эффект»; флаг без живой панели —
  либо реализовать, либо честно `KEEP_EXPERIMENTAL` с датой (решения 004/011).
- G2 усилен: юнит на контракт. G5: для UI — визуальная проверка (скриншот с SHA).

**DoD-дельга.** Нет «мёртвых» кнопок и вечных «Скоро» без записи решения; каждый
негативный путь bounded + typed + actionable; i18n-ключи добавлены во все 12 локалей.

**Отчёт-дельта.** Execution matrix по формату `00-orchestrator.md` §11 (`Задача | Субагент | Скилл(ы) | Ветка | Коммит | Гейты | PR | Деплой | Статус`) + per-item BEFORE / ROOT CAUSE / FIX / TEST / RUNTIME / REMAINING.

**Грабли репо.** Один общий файл — ровно один владелец (см. ownership map в
`plans/next-program-prompt.md`); не трогать чужие срезы; протокольные DTO — один владелец.

---

## 2. Bugfix (repro → root cause → fix → regression test)

**Когда.** Наблюдаемое неверное поведение: падающий тест, баг, флейк, регресс.

**Фазовые дельты.** Фаза SPEC короче: вместо полного дизайна — **repro + root cause**.
Порядок обязателен: (1) воспроизвести на чистом дереве, (2) локализовать корневую причину
(не симптом), (3) фикс, (4) регрессионный тест, который падал до фикса и проходит после.

**Гейт-дельты vs G0–G7.**
- G0–G1 сжаты: acceptance = «баг воспроизведён до, устранён после», приложен repro.
- G2: failing test — **до** фикса (red → green), а не после.
- G3–G5 без изменений. G4 не отменяется, если баг в auth/secrets/upload/callback.

**DoD-дельга.** Регрессионный тест существует и краснел без фикса; флейк отличается от
реального падения: флейк маркируется владельцем и сроком, а не «чинится» повтором
(см. журнал `docs/plans/lane-process.md`).

**Отчёт-дельта.** BEFORE / ROOT CAUSE / FIX / TEST / RUNTIME / REMAINING на каждый баг;
для флейка — число прогонов + разброс.

**Грабли репо.** Два прогона подряд должны давать **идентичный** набор падений
(детерминизм; так закрыли T7 — каталог `handlers`); «локально-красный, CI-зелёный» — это
среда, а не баг (раздел 7 `lane-process.md`).

---

## 3. Prefactor / Refactor (швы, expand–contract, deletion test)

**Когда.** Поведение не меняется, но следующий дифф должен перестать сериализоваться через
god-модуль (пример: `packages/server-core/src/sessions/SessionManager.ts`, тикет 09).

**Фазовые дельты.** Prefactor идёт **первым** (WAVE 0), до фич. Стиль — expand–contract:
сначала ввести шов рядом со старым путём, перевести callers, затем удалить старый.

**Гейт-дельты vs G0–G7.**
- SPEC фиксирует **тот же публичный интерфейс** и внутренние швы; deletion test пишется
  заранее («если вернуть extract обратно — сложность расползётся по callers?»).
- G2 усилен: поведенческие тесты не меняются; доказывается, что наблюдаемое поведение то же.
- G4 обычно N/A (нет нового ввода) — фиксируется явно как «поверхность не изменилась».

**DoD-дельга.** Deletion test пройден (шов стоит, callers не дублируют); dead code/обёртки
«на всякий случай» удалены (как `SessionViewTabs.tsx` в решении 007); следующий дифф по
области — не в 10k-строчном файле.

**Отчёт-дельта.** «Что вынесено» + Deletion test + список callers, переведённых на шов.

**Грабли репо.** Не расширять публичный контракт под видом рефакторинга; не заводить
вторую конвенцию — только существующий паттерн.

---

## 4. Migration (данные / конфиг / совместимость)

**Когда.** Миграция схемы/DDL (`apps/workspace-service/migrations/*`), конфига, legacy-алиасов
или совместимости протокола.

**Фазовые дельты.** SPEC включает **план отката** и upgrade-path (старые данные читаются после
миграции). Для БД — тест на throwaway Postgres (`ROX_TEST_PG_URL`, job `workspace-migrations`).

**Гейт-дельты vs G0–G7.**
- G2 усилен: upgrade-path + startup + `EXPLAIN` (см. `workspace-service:test:migrations`).
- G4 обязателен при миграции секретов/PII.

**DoD-дельга.** `ROX_*` читается, **`CRAFT_*` legacy-алиасы живы и сохранены** (не
переименовывать вслепую — `AGENTS.md`, «старые идентификаторы для безопасного импорта»);
freeze-closed пути (G2 SiYuan, appId) не ослабляются; старые данные импортируются
копированием, источник сохраняется.

**Отчёт-дельта.** До/после на реальном (или контейнерном) Postgres + версия схемы + откат.

**Грабли репо.** `bun.lock` при конфликте **не** мёржить руками — перегенерировать;
миграции workspace-service упакованы в `workspace-service:package` (список файлов — истина).

## 5. Decision-only (ADR в `plans/*/decisions/`, никогда не становится кодом)

**Когда.** Нужно решение (продуктовое/юридическое/архитектурное), а не реализация. Пример:
`plans/next-program/decisions/001-g2-managed-siyuan.md`, `007-session-views-honesty.md`.

**Фазовые дельты.** Выход — ADR по грамматике репозитория: заголовок `# NNN — Title`,
`Status`, `Owner`, `Context`, `Decision`, при необходимости `Runtime` / `What would flip
this` / `Evidence`. Кода нет; сама запись — документ (коммитится через PR).

**Гейт-дельты vs G0–G7.**
- G1–G5 и G7 не применимы (нечего собирать/тестировать/деплоить) — фиксируется явно.
- G0 остаётся. Решение принимает **человек** — это стоп-класс ④ (`00-orchestrator.md` §2); агент готовит запись, не решает.

**DoD-дельга.** Решение записано, статус (`ACCEPTED`/`REJECTED`) и владелец указаны,
зафиксировано «что перевернёт это решение». Decision-ticket не превращается в код.

**Отчёт-дельта.** Ссылка на ADR + решение владельца + что осталось человеком.

**Грабли репо.** Не бандлить SiYuan; не flip `appId`/`productName`; не включать unified
shell по умолчанию (решения 001/004). Если решение блокируется юр./политикой — это BLOCKED,
а не «сделаю сам».

## 6. Release / Deploy

**Когда.** Выпуск десктопа, образа сервера или WebUI-ассетов.

**Фазовые дельты.** G6–G7 становятся основными: сборка → публикация → live smoke. Пути:
- Десктоп: ветка `release/desktop-*` → `desktop-release.yml` (`bun scripts/desktop-release.ts`,
  матрица `macos-15` + `windows-2025`), затем `publish-desktop-release.yml` (`workflow_dispatch` с `run-id`
  и `tag`) → `scripts/publish-desktop-release.ts`.
- Сервер: `Dockerfile.server` (`bun run server:build:subprocess`, порт `9100`,
  `ROX_SERVER_TOKEN`).
- WebUI: `bun run webui:build`.

**Гейт-дельты vs G0–G7.**
- G1/G2 как в base, плюс release-специфичные наборы, вшитые в `desktop-release.yml`.
- G7 обязателен и содержит **production OPS** — Cloudflare/R2/Pages **человеком**, не агентом
  (запрет из `plans/next-program-prompt.md`).

**DoD-дельга.** Артефакты (`.dmg/.zip/.exe`, `latest*.yml`, `manifest-*.json`) собраны;
live smoke пройден; каждый OPS-шаг назван как человек-чеклист.

**Отчёт-дельта.** Таблица артефактов + SHA ревизии + статус VERIFIED / MOCK-VERIFIED /
BLOCKED + «что осталось человеком (CF rule, R2 cleanup)».

**Грабли репо.** Не репортить модель, которую OMP не использовал; не оставлять permanent
spinner; не удалять remote-ветки; ключи подписи (`CSC_LINK`, `APPLE_*`) — секреты CI, не в код.

---

## 7. Incident / красный main

**Почему отдельный архетип:** у него жёсткий SLA 15 минут, собственный протокол отката и
запрет новой работы — это отдельный режим, а не дельта к feature-циклу.

**Когда.** `main` красный (кроме явно внешнего сервиса).

**Фазовые дельты.** Все фазы встают: сначала локализация → фикс/откат, только потом новое.
Кто слил красное — чинит первым делом (`docs/plans/lane-process.md`, п.1).

**Гейт-дельты vs G0–G7.**
- G0–G7 базового среза приостановлены.
- Мини-цикл: repro на чистом дереве → root cause (или вердикт «внешнее») → фикс или
  `git revert` / возврат main к зафиксированному SHA (force запрещён) → зелёный `freshness`.

**DoD-дельга.** Красный main не дольше 15 минут; внешний отказ эскалирован владельцу, а не
«вылечен» кодом; запись в журнал инцидентов с SHA.

**Отчёт-дельта.** Инцидент / SHA / действие / статус (как таблица в `lane-process.md` §4).

**Грабли репо.** Перегруз очереди Actions: серийный train, ручная свежесть (`update-branch` +
дождаться), `--admin --merge` — только last resort и с фиксацией (аварийный протокол §6).
