# WP-48: linkage of emitted bundles to exact component bytes

Status: proposed checker extension, verified with isolated fixture builds and final archives. No human license decision, canonical audit command, production publication, or WP-48 acceptance is implied.

## Contract and ownership

The existing `ReleaseSchema`, `ProduceSBOM`, `componentDigest`, `ValidateReleaseNotices`, and `CheckRelease` remain the release checker. Each ordinary file retains `componentId`. An emitted file instead declares `contributions`: one entry per component, containing its `scopeSha256` and positive emitted inputs (`path`, current `sha256`, and `bytesInOutput`). Exactly one ownership form is allowed. A common bundle is never assigned wholesale to one component.

An artifact's optional `bundle` binds the captured source tree digest, build directory, output directory, lock bytes, metafile bytes, and package scopes. Paths are relative to audited staging or the captured source root. The capture must contain each graph input, its actual nearest package manifest, applicable registry license bytes, workspace/root notices, exact lock, metafile, and emitted outputs. Registry archives stay under staging and are referenced by path and digest. Evidence files are not automatically distributed payload files.

`buildFlags.bundled: true` requires this proof. Independently trusted review policy can set `requiredBundleArtifacts` to the exact artifact IDs; this denies a producer disabling the flag or deleting the proof. An absent policy is not evidence that a program is unbundled. The protected review revision must include the policy for every known bundled release variant. The existing review manifest/checker revision binding remains necessary.

The checker reconstructs the graph from snapshot bytes. It checks exact package manifest name/version and scope, unique physical input/output paths, exact workspace lock entries or unique registry pins, SHA512 archive integrity, actual archive source members and notices, emitted output digests, and all claimed contributions per output. Missing, extra, duplicated, ambiguous, or changed evidence produces findings. The captured tree and lock/metafile are checked again after reconstruction. Final archive members must still equal the distributed staging inventory.

Component digests and the SBOM include the linked inputs and bundle proof. Scope/contribution/input order is canonicalized. Any change invalidates applicable scoped review. Notices apply to every component contributing to an artifact. Existing origin conflicts, copy review, approved decision matching, and actual final archive validation still run.

## Proof and limits

The isolated acceptance suite runs real Bun builds with a local registry-shaped package, verifies its actual SHA512-pinned tar archive, and audits the final tar. Both a mixed output and a second workspace-only output are exercised. Negative cases cover single-owner substitution, missing proof/scope/input, duplicate components and output aliases, unknown IDs, same-length source alteration, changed metafile digest, changed registry bytes with refreshed outer digest, forged workspace version with refreshed lock/source digests, and replaced emitted bytes. The original full archive/CLI/symlink tests and the five collector suites run without filters.

A negative control shows that a real dependency bundled into an output can be cleared under only workspace ownership by the installed checker without independent bundle policy. Adding `requiredBundleArtifacts` denies the same bytes and claim. Qualified-review strings in tests are explicitly synthetic fixture data.

This gate checks byte linkage, not compiler authenticity. A producer-controlled graph plus source capture cannot by itself prove that those sources produced the output. Source revision binding currently names the Git base; dirty/untracked changes require their separate lineage/diff evidence. Reproducible build or authenticated trusted-producer attestation, deployed Bun/native builtin provenance, complete dynamic dependency inventory, and upstream/copy/license applicability review remain separate requirements. The historical runtime v3 receipt is not refreshed by this change. No component is assigned a license merely because the ROX root carries one.

The fixture registry package is not a claim about an npm registry publication. For an actual release the existing registry collector must read the real registry metadata/archive, bind it to the lock, and retain exact bytes. Missing source origin revisions cannot be filled with invented hashes to create a release manifest.

## Next canonical `audit.releaseLicense` integration request

The normative operation is presently absent from the composed authority. Implement it through the same transport Actor and domain command boundary already used by `apps/workspace-service/src/server.ts`, `http.ts`, `modules/identity/commands.ts`, and `modules/identity/repository.ts`, with shared contracts in `packages/shared/src/workspace-domain`. Add a bounded release module; do not turn the standalone checker into a second command system.

1. Define a strict schema-version-2 `RoxCommand` payload naming the immutable release/component manifest and final artifact digests, expected release revision, checker revision, review revision, policy digest, lock digest, source revision plus dirty-source lineage digest, authenticated producer evidence digest, notices digest, and exact build variant. Reject payload Actor, reviewer grants, workspace substitutions, mutable paths/URLs, unknown fields, and unbounded evidence. Human review records are independently supplied and verified; the command cannot invent one.
2. Resolve the canonical release Resource within the route workspace. Require Resource read, write, and action grants for `audit.releaseLicense`, recheck linked artifact/component/notice/producer/review resources at execution, and bind policy epoch. A workspace membership or an execution allow-all setting is insufficient. Use existing authenticated Actor construction and PostgreSQL session lock/revocation gate. Return constant authorization failures without disclosing hidden artifact names or review text.
3. Store only the release component manifest and audit result in the authoritative PostgreSQL release aggregate. Add versioned migration and repository ports. Validate immutable evidence digests and trusted roots before running the existing checker. Run untrusted archive/metafile parsing under bounded admission outside the commit transaction, then recheck all linked immutable evidence and authorization in the transaction before commit.
4. Serialize expected-revision compare-and-swap, Actor/workspace/action/idempotency request binding, durable audit receipt, release revision, and `audit.license_reviewed` event in the same transaction. A denied/license-review-required result cannot produce an approved publication receipt. Receipt reconstruction must validate database JSON against immutable row/evidence bindings; replay cannot trust stored typed JSON or mutable review fields.
5. Append the event through the existing durable event/outbox contract and serialization rule, with references/digests only. Do not overload `project.created` or leak license/reviewer/secret payloads. Authorized replay and receipt readback must preserve Actor/workspace/policy boundaries. Add tests for two-account denial, grant changes/session revocation, linked-reference replacement, simultaneous idempotency, revision conflict, restart recovery, malformed receipt JSON, and event privacy. No synthetic approval, dead-letter claim, or delivery claim substitutes for these tests.
6. Bind publication to the committed receipt, final artifact hashes, authenticated producer build evidence, independently trusted checker/review revisions, and persisted audit digest. Wire the actual producer/publisher workflow to the existing reusable license gate. Its current presence alone does not prove that a publisher calls it. Preserve evidence on denial; do not mutate user projects, notes, messages, or identities to perform a release audit.

Root owns integration and existing-source changes. This proposal does not close the canonical operation, permission, human review, provenance, runtime inventory, or publication gates.
