# Защита main и «интерфейс → код» — исполнимый план (2026-10-10)

**Цель (наблюдаемый результат):** главная ветка защищена четырьмя выбранными правилами, и это **не тормозит работу**; конвейер проверок ускоряется; долг «известно красных» сокращается к нулю; **каждый элемент интерфейса, который сейчас обещает функциональность, получает реальный код** (17 пунктов инвентаря, Приложение A); появляется наблюдаемость здоровья main и рабочий процесс для параллельных агентов.

**Spec (что считаем источником):**
- Решения владельца (сессия 2026-10-10): включить 4 правила — запрет принудительной перезаписи, запрет удаления main, запрет прямой записи (только через запросы на слияние, 0 одобрений), обязательная свежесть ветки; остальные правила не включать. Цели: работа не встаёт, доделываем максимально быстро, под интерфейс появляется код.
- Инвентарь «интерфейс без кода» (17 пунктов) — разведка `UiNoCodeInventory` (2026-10-10); авторитетная копия — Приложение A ниже.
- Реестр программы: `docs/plans/2026-10-09-platform-program.md`; конвенции тикетов: `plans/next-program/README.md`, `plans/next-program/tickets/*`.

**Authority and constraints:**
- Изменения в main — только через запросы на слияние (правило уже действует с 2026-10-10, набор правил `main-protection`).
- Обязательных «тяжёлых» проверок не добавляем; свежесть обеспечивает сверхлёгкая проверка-носитель `freshness` (секунды).
- Не включаем: одобрения, линейную историю, подписи, ограничение круга слиятелей, правила меток, очередь слияния (резерв на случай, если трение окажется велико).
- Существующие изменения других лейнов не трогаем; каждый срез — своя ветка; общий файл — ровно один владелец.

**Architecture (решение):**
- Набор правил репозитория (`rulesets`) id `24843533`, условия `~DEFAULT_BRANCH`: `deletion`, `non_fast_forward`, `pull_request` (0 одобрений, все способы слияния), `required_status_checks` (strict = true).
- GitHub игнорирует strict-свежесть без хотя бы одной обязательной проверки (проверено зондом #1788: отставшая ветка осталась MERGEABLE). Поэтому носитель — `main-freshness` (PR #1789, контекст `freshness`), тривиальная работа, чей единственный смысл — включить механизм свежести.
- Интерфейсный слой: «код под интерфейс» строится по контракту «действие в интерфейсе → реальный эффект», через существующие слои IPC/RPC; никакого фальшивого кода-имитации.

**Current state (проверено 2026-10-10):**
- Набор правил `24843533` активен; `rules/branches/main` возвращает `deletion`, `non_fast_forward`, `pull_request`, `required_status_checks`.
- Носитель: PR #1789 (ветка `ci/main-freshness-check`, коммит `46ecb44e`), проверка `freshness` в очереди; фоновый дозор (`bg_49`) сольёт PR при зелёном.
- Ни один рабочий процесс и скрипт репозитория не пушит в main напрямую — запрет прямой записи ничего не ломает.
- 23 файла рабочих процессов; ночной агрегат `nightly-test-all.yml` + `scripts/test-all.ts` + `scripts/test-baseline.json` (130 «известно красных», уже отслеживаются `newFailures` и `stalePass`).

## Decisions and alternatives

1. **Наборы правил, а не классическая защита ветки** — единый механизм, условия по умолчанию ветке, поддержка дефолтной ветки в условиях. Классическая защита не использована (дублирует и не покрывает всё).
2. **Свежесть через сверхлёгкий носитель, а не через обязательные реальные проверки** — цель «не встать»; носитель стоит секунды. Если GitHub когда-нибудь позволит strict без проверок — носитель можно убрать.
3. **Выключен `require_extra_approval_for_unattributed_changes`** — дефолт GitHub добавлял бы лишние одобрения у лейнов.
4. **Отклонено владельцем:** одобрения (мин. N), линейная история, подписанные коммиты, ограничение круга слиятелей, правила меток. Очередь слияния — не включаем сейчас, но держим как резерв при росте трения.
5. **UI: сначала «ложные обещания» интерфейса, потом крупные бэкенды** (почта/звонки/командные чаты) — так видны максимальные улучшения за минимальное время.
6. **Волны и порядок:** W1 — T1–T2, T5, T8, T11; W2 — T3–T4, T7, T9, T10, T12; W3 — T6 → T14, T13, T15-итог (T6 строго до T14 — отчёт потребляет результат триажа).
