# Процесс лейнов (T15)

Рабочие правила для всех лейнов (`slice/*`), дополняющие план
[`2026-10-10-main-guardrails-and-ui-to-code.md`](./2026-10-10-main-guardrails-and-ui-to-code.md).
Файл самодостаточен: правила, порядок фиксации точек отката и журнал инцидентов — ниже.

## 1. Правила

1. **Кто слил красное в main — чинит первым делом.** Красный main (кроме явно внешнего, п. 5) —
   стоп новой работе: локализуй, почини или откати; новое начинается только после зелёного main.
   Цель — красный main не дольше 15 минут.
2. **Перед крупной волной — точка отката.** Ветка-срез и её SHA фиксируются в плане или описании
   PR **до** начала волны. Это известное доброе состояние, к которому можно вернуться.
3. **Самопроверка среза.** Перед слиянием срез прогоняет: (а) затронутые наборы тестов,
   (б) проверку типов, (в) для UI — визуальную проверку. Результат фиксируется в PR.
4. **Доказательства привязаны к ревизии.** Все артефакты (логи, скриншоты, замеры, вывод тестов)
   указывают SHA проверяемой ревизии; «примерно на этой ветке» не считается доказательством.
5. **Внешнее кодом не чинится.** Отказ внешнего сервиса (Vercel, провайдер и т. п.) фиксируется
   как внешний и эскалируется владельцу, а не «лечится» правкой кода.

## 2. Точка отката и откат

- **Фиксация:** `ветка-срез @ <SHA>` + дата — в плане/PR до волны. Для волны точкой отката служит
  коммит main непосредственно перед первым слиянием волны.
- **Сам срез тоже точка отката:** каждая ветка `slice/*` до слияния — кандидат на самостоятельный
  откат; слияние идёт только через PR (правила main: `deletion`, `non_fast_forward`, `pull_request`,
  `required_status_checks`/`freshness`).
- **Действие отката:** `git revert` диапазона слияний волны либо возврат main к зафиксированному SHA
  (force не разрешён — только revert/PR).

## 3. Самопроверка среза — чек-лист

| Проверка | Что приложить в PR |
|---|---|
| Затронутые наборы тестов | команда + результат (лог/счётчик) |
| Типы | команда + результат (`tsc`/аналог) |
| Визуал (только UI) | скриншот + SHA ревизии |

## 5. Приёмка T15

- 2 недели без красного main дольше 15 минут (наблюдение — отчёт T14 «здоровье main»).
- Перед каждой волной существует точка отката (запись в разделе 4).

## 6. Аварийный протокол: перегрузка очереди Actions (утверждён владельцем 2026-10-13)

**Триггер.** Обязательная проверка `freshness` (или иная required) не стартует >30 минут: очередь `queued` многократно превышает `in_progress` (наблюдение 2026-10-13: 131 queued при 8 in_progress; `freshness` не стартовал >1 ч).

**Действия.**
1. **Серийный train:** сливаем по одной ветке; `update-branch` — только для активной ветки; веерные обновления запрещены (умножают очередь).
2. **Ручная свежесть:** перед слиянием ветка обязана содержать актуальный `origin/main` (`update-branch` + дождаться завершения). `BEHIND`/`DIRTY` — стоп, не сливать.
3. **Админ-обход — только last resort:** `gh pr merge --admin --merge` допустим лишь при выполнении п.2 и только для проверенных PR; **каждое применение фиксируется** комментарием в issue волны (PR, merge-SHA, причина) — пример: issue #1820, слияния 2026-10-13 12:14–12:25Z.
4. **Гигиена ранов:** не пушить веерно; отменять свои устаревшие квиуед-раны необязательных проверок; при системной перегрузке — `paths-ignore`/объединение мелких воркфлоу.
5. **Возврат к штатному режиму:** при первой возможности (очередь дренится) — обычное авто-слияние; обход не становится привычкой. Инженерное устранение причины: #1843 — `freshness` переведён на Blacksmith-раннеры (2026-10-13).

**Приёмка:** каждый обход задокументирован; ни одна ветка не слита устаревшей; после разгрузки — штатный цикл.

## 7. Baseline и среды (решение владельца 2026-10-13)

`knownRed` обновляется **по ночному CI stalePass** (механизм T5/#1819): источник истины — nightly на Linux-раннерах. Локальные macOS-прогоны могут видеть собственные «новые» (env/нагрузка) — это ожидаемо и не меняет baseline; систематическое расхождение класса «локально-красный, CI-зелёный» фиксируется в issue волны.
