# PRD — ROX Product Learning

> Актуализация main: см. [дополнение по PR #1394](08-LATEST-MAIN-DELTA.md). Подробные исходные ссылки остаются закреплены за SHA аудита.

**Версия:** 1.0, 3 октября 2026 года.\
**База аудита:** `rox-one/rox-one`, `main` на коммите `192558583b3f7acc84e0636a4e5fc7ba8d9a7435`.\
**Статус:** требования и пакет для реализации. Изменений приложения, pull request и запуска продуктовых тестов в рамках подготовки этого пакета не было.

## 1. Продуктовое решение

Построить добровольное обучение внутри настоящего интерфейса Rox: затемнение с выделением элемента, короткая подсказка, действие пользователя, подтверждение результата. Первый маршрут состоит из шести шагов и заканчивается новым ответом на собственный запрос. Остальные возможности раскрываются отдельными контекстными маршрутами, а не обязательным обходом меню.

В поставку входят **25 сценариев и 56 атомарных шагов**. Это уточнение предыдущего предложения: один пункт вроде «Attachments + Voice» или «Meetings + Feed» нельзя превращать в одну перегруженную подсказку. Полный перечень находится в [каталоге](04-TOUR-CATALOG.md); его машиночитаемый источник — [tour-catalog.json](tour-catalog.json).

Тур — слой обучения, а не агент, не механизм авторизации и не новая система исполнения задач. Он наблюдает реальные состояния приложения и направляет пользователя к существующим действиям. Он не получает полномочий отправлять запросы, менять разрешения или создавать пользовательские данные самостоятельно.

## Контракт автономного исполнения

Реализация выполняется **end-to-end без дополнительных согласований с пользователем**. После запуска coding agent не останавливается для подтверждения архитектуры, отдельных патчей, тестового плана, создания веток, push, pull request или merge. Некритичную неоднозначность он разрешает самостоятельно в пользу наиболее совместимого, обратимого и проверяемого варианта и фиксирует решение в итоговом отчёте.

После короткого автоматического bootstrap (`OB-00` + `OB-01`) все независимые работы запускаются **одним параллельным fan-out A1–A11 от одного `CONTRACT_SHA`**. A0 остаётся активным integration lane: принимает готовые worker commits по мере их появления, разрешает конфликты общих файлов, прогоняет affected checks и не ждёт завершения остальных workers, чтобы начать интеграцию уже готовых результатов. Исправления после интеграционных проверок возвращаются владельцу сразу и выполняются в той же волне, без новой стадии согласования.

Финал обязателен: A0 собирает полный candidate, выполняет release-blocking проверки, исправляет внесённые регрессии, синхронизируется с актуальным `origin/main`, повторяет затронутые проверки, затем **самостоятельно публикует изменения и доводит их до merge в `main`**. Если политика репозитория требует PR, A0 создаёт PR, отслеживает CI, исправляет ошибки и мержит его без запроса подтверждения пользователя. Если разрешён и принят репозиторием прямой merge/push в `main`, допустим этот путь. Запрещено обходить branch protection, security controls или подделывать статусы проверок; если существует внешний технически непреодолимый gate (например, обязательный review другим аккаунтом), агент завершает всё остальное, оставляет merge-ready PR и указывает точный внешний blocker вместо запроса на дополнительное решение.

Это разрешение относится к **разработке и доставке кода**. Оно не меняет продуктовый инвариант walkthrough: сам Product Tour не должен автоматически отправлять пользовательские запросы, выдавать permissions, включать микрофон, импортировать credentials, запускать automation или публиковать пользовательские Pages от лица конечного пользователя.

## 2. Проблема

В Rox одновременно существуют сессии, личные задачи, проекты, Notes, Pages, Memory, источники, навыки, подключения и автоматизации. Названия разделов не объясняют различия. Пользователь может принять Inbox за историю чатов, Tasks за доску сессий, Sources за готовые подключения, а Connections за выбор модели.

Эти различия подтверждаются не маркетинговым описанием, а текущими маршрутами и компонентами: [routes.ts](https://github.com/rox-one/rox-one/blob/192558583b3f7acc84e0636a4e5fc7ba8d9a7435/apps/electron/src/shared/routes.ts), [TasksPage](https://github.com/rox-one/rox-one/blob/192558583b3f7acc84e0636a4e5fc7ba8d9a7435/apps/electron/src/renderer/pages/TasksPage.tsx), [ConnectionsPage](https://github.com/rox-one/rox-one/blob/192558583b3f7acc84e0636a4e5fc7ba8d9a7435/apps/electron/src/renderer/pages/ConnectionsPage.tsx). Уровень проверки каждого файла указан в [аудите](03-CODEBASE-AUDIT.md).

## 3. Цели

| Цель | Что должно измениться | Как проверить |
|---|---|---|
| G1. Первая польза | Новый пользователь отправляет собственный запрос и видит новый финальный ответ без обязательной настройки всех разделов | E2E первого маршрута; локальная метрика времени до доставки ответа |
| G2. Осознанный контроль | Пользователь видит текущий режим, различает разрешение, запуск и сортировку очереди | Негативные тесты: тур ничего не отправляет и не разрешает; отказ в запросе является корректным решением |
| G3. Повторное использование | Пользователь умеет подключить контекст, сохранить материал и найти его снова | Отдельные подтверждения источника, заметки, памяти, поиска; не только просмотры подсказок |
| G4. Устойчивое обучение | Тур переживает изменение панели, размера окна, перезапуск и временную недоступность | Тесты нескольких панелей/окон, storage failure, route restoration, compact layout |
| G5. Управляемая поставка | Все сценарии имеют владельца, критерий завершения и тест | Полная трассировка каталог → target → adapter → task → test |

У нас нет измеренного baseline конверсии или удержания. PRD не обещает процентный рост и не объявляет выбранные UX-параметры эмпирически оптимальными. Сначала измеряется исходное поведение, затем сравниваются варианты приглашения и порядка маршрутов.

## 4. Пользователи и входы

**Новая локальная установка.** Существующий setup остаётся первым. Создание welcome-сессии уже реализовано и не требует LLM: [первый разговор](https://github.com/rox-one/rox-one/blob/192558583b3f7acc84e0636a4e5fc7ba8d9a7435/docs/builtin-mcp-onboarding.md). После него появляется компактное предложение «Покажи, как получить первый результат», без автоматического затемнения поверх набираемого текста.

**Пользователь с историей.** Отсутствие нового ключа product-tour не делает его новичком. Никакой автоматической серии на обновлении. Доступны Settings → Обучение, ручной запуск и ненавязчивое предложение при первом использовании конкретной функции.

**Пользователь WebUI или удалённого workspace.** Доступны только маршруты и операции, разрешённые реальным окружением. Нельзя обращаться к локальным файлам сервера или запускать desktop-setup на основании одного `workspaceId`. Ручной запуск работает и без подтверждённого статуса новой установки.

**Пользователь клавиатуры или экранного диктора.** Каждый маршрут доступен без мыши. Выделенный элемент остаётся доступным; подсказка не запирает focus отдельно от элемента, который предлагает нажать.

## 5. Путь к первому результату

1. Использовать существующую welcome-сессию; при её отсутствии пользователь сам создаёт сессию.
2. Посмотреть фактический режим разрешений, не меняя его автоматически.
3. Ввести задачу или продолжить сохранённый черновик.
4. Нажать обычную кнопку отправки; дождаться принятия сообщения приложением.
5. Увидеть выполнение и место управления им. Если запрос завершился быстро, показать завершённый ход, а не искусственную загрузку.
6. Открыть новый финальный ответ и оценить его применимость.

Статический welcome и intermediate text не являются результатом этого маршрута. Успешная доставка ответа — техническая метрика, а не утверждение, что пользовательская задача решена правильно. Успешный вызов инструмента и оценка полезности учитываются отдельно.

## 6. Требования к опыту

**FR-01. Добровольность.** Start, Pause, Resume, Back, Skip step и Dismiss должны иметь различимые значения. Закрытие/Esc ставит маршрут на паузу. Пропущенный шаг не считается выполненным действием.

**FR-02. Одна мысль на шаг.** Заголовок, короткое объяснение, ожидаемое действие, локальный прогресс. Полные тексты RU/EN подготовлены в `copy/`; в продукте они импортируются в существующую систему `t()`.

**FR-03. Реальные цели.** Подсветка привязана к DOM-элементу конкретного workspace/panel/session. Запрещены скриншоты вместо интерфейса, CSS-селекторы по расположению, глобальный выбор первого совпадения и цели внутри недоверенного iframe.

**FR-04. Настоящее подтверждение.** Открытие меню, выбор значения и сохранение на сервере — разные стадии. Шаг с сохранением заканчивается после подтверждения существующей операции или чтения актуального доменного состояния. Оптимистический UI не является доказательством записи.

**FR-05. Контекстная доступность.** Выключенная функция, отсутствующее право, неподдерживаемая ОС, загрузка источника и отсутствие нужного объекта получают разные причины недоступности. Нельзя показывать фиктивные данные ради прохождения.

**FR-06. Независимость от настройки всех MCP.** Первый маршрут не ждёт завершения установки встроенных источников. Sources объясняет различие «выбран», «настраивается» и «готов».

**FR-07. Центр обучения.** Новая native settings-page `learning`: 25 сценариев по смысловым группам, прогресс, продолжение/повтор, объяснение недоступности, управление приглашениями, отдельный сброс только обучения. Никакой новой обязательной верхнеуровневой панели.

**FR-08. Согласование существующих подсказок.** Setup, first-session welcome, Memory seed dialog, Quests и product-tour не конкурируют за экран. Memory marker сохраняется только при реальном взаимодействии со старым Memory dialog, а не при откладывании его показа.

**FR-09. Сохранение работы.** Тур не заменяет черновик, не очищает вложения, не возвращает старый маршрут поверх ручной навигации и не отменяет настоящие операции при Back/Close. Пример можно вставить только отдельной кнопкой в пустой черновик.

**FR-10. Платформы.** macOS и Windows, обычная и компактная оболочка, WebUI, текущий zoom и обе темы. Для записи, файловых диалогов и недоступных desktop API — отдельные ветви и объяснения.

**FR-11. Локальные данные обучения.** Прогресс не является учётной записью и не синхронизируется между устройствами в этой поставке. Он хранится в профиле клиента и workspace. При недоступном хранилище обучение остаётся ручным и работает в памяти.

**FR-12. Диагностика без контента.** По умолчанию нет нового удалённого аналитического SDK и отправки событий. Опциональный локальный журнал не содержит текстов, путей, URL, ключей, имён документов и содержимого ответов.

## 7. Запреты и границы

Тур не меняет дефолт `allow-all`, не расширяет список циклических режимов и не назначает себе роль контролёра разрешений. Эти изменения требуют отдельного продуктового решения.

Тур не запускает LLM-запрос, OAuth, импорт credentials, запись микрофона, автоматизацию, публикацию Page или запись Memory без обычного явного действия пользователя. Закрытие тура не отменяет уже разрешённую пользователем задачу.

Наличие файла страницы в репозитории не доказывает её исправность в конкретном runtime. Не входят: создание недостающих почтовых/meeting RPC, переработка OMP, новый файловый индекс, Open Notebook, публичная аналитика/лидерборд, биллинг и синхронизация обучения между аккаунтами.

Эти границы не сокращают каталог: все 25 сценариев должны быть реализованы, локализованы и протестированы с готовой, пустой и недоступной ветвями. Временно недоступные функции остаются видимыми в центре обучения с причиной; это не считается выполнением их действий.

## 8. Критерии готовности продукта

| Критерий | Порог при приёмке |
|---|---|
| Покрытие | 25 сценариев, 56 уникальных шагов, 100% имеют target mapping, правила evidence и проверки |
| Первый маршрут | Все 6 шагов проходят через реальные компоненты и обычный transport; источник модели в E2E может быть детерминированной тестовой заменой |
| Безопасность | Ноль автоматических send/approve/OAuth/record/share/run/secret-import со стороны tour engine |
| Прогресс | Resume/replay/reset, миграции и отсутствие потери прогресса при конкурентной записи в одной storage partition |
| Доступность | Ручная клавиатурная проверка и автоматические проверки имён/focus; критических блокирующих ошибок нет |
| Совместимость | Проверены macOS/Windows; WebUI и restricted runtime не вызывают недоступные методы |
| Честность | Welcome/intermediate/error/cancel/optimistic update не проходят тесты как verified success |
| Регрессии | Нет новых ошибок обязательных typecheck/lint/test; прежние ошибки зафиксированы сравнением baseline, а не замаскированы |
| Откат | Один feature flag отключает host и наблюдателей без изменения пользовательских данных |

## 9. Метрики

Основной показатель: время от явного Start первого маршрута до нового доставленного final response на пользовательский запрос. Отдельно считать время до принятия запроса, завершение без ответа, отмены, ошибки и выходы. Нельзя рассчитывать показатель только по тем, кто успешно закончил маршрут, и скрывать остальные исходы.

Показатели освоения: первый подтверждённый Source tool result, сохранённая Note, созданная PersonalTask, добровольная Memory запись, повторно открытый материал поиска. Просмотр меню и отметка старой Quest не увеличивают эти счётчики.

Диагностические показатели: missing target по варианту оболочки, blocked capability по причине, ошибки сохранения, паузы при переключении панели, время подготовки шага. Изменение порядка подсказок проверять контролируемым сравнением; эксперимент не даёт разрешения отправлять пользовательский контент.

## 10. Порядок поставки

Контракты и аудит изменений → параллельная разработка независимых модулей → единая интеграция → приложение целиком и native-проверки → ручное включение на внутренних установках → включение приглашений для новых установок. Маршруты P1/P2 — порядок разработки, а не право удалить их из поставки.
