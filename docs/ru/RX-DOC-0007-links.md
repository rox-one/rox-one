# Смежные репозитории и валидатор кодов RX-*

Документ описывает, как основной публичный репозиторий `rox-one/rox-one`
связан с приватными смежными репозиториями, какой компромисс выбран из‑за
разной видимости, и как запускать валидатор идентификаторов `RX-*`.

Связанные записи: `RX-TSK-0700`, `RX-TSK-0701`, `RX-PIP-0200`, `RX-PIP-0201`.

## 1. Зачем нужны смежные репозитории

Два соседних репозитория организации `rox-one` живут отдельно от публичного
кода продукта:

| Каталог в дереве | Удалённый репозиторий | Назначение | Видимость |
|---|---|---|---|
| `vendor/rox-one-assets` | `github.com/rox-one/rox-one-assets` | Брендбук, плашки, карта доменов | приватный |
| `vendor/rox-one-website` | `github.com/rox-one/rox-one-website` | Сайт, кабинет, биллинг | приватный |

Сам `rox-one/rox-one` — **публичный**. Если объявить обычные сабмодули на
приватные репозитории, внешний `git clone --recurse-submodules` получит
нерабочую ссылку и упадёт на аутентификации. Это и есть конфликт, который
решает схема ниже.

## 2. Как устроены сабмодули

Записи живут в `.gitmodules`. Ровно два сабмодуля, оба с `update = none`
и `shallow = true`:

```
[submodule "vendor/rox-one-assets"]
	path = vendor/rox-one-assets
	url = https://github.com/rox-one/rox-one-assets.git
	update = none
	shallow = true
[submodule "vendor/rox-one-website"]
	path = vendor/rox-one-website
	url = https://github.com/rox-one/rox-one-website.git
	update = none
	shallow = true
```

Что означают ключи:

- `path` — каталог внутри публичного дерева. Префикс `vendor/` подчёркивает:
  это чужой (смежный) код и ассеты, не часть публичного продукта.
- `url` — HTTPS-адрес без встроенного токена. Учётка не должна попадать
  в публичный `.gitmodules`.
- `update = none` — `git submodule update` и `git clone --recurse-submodules`
  **пропускают** эти сабмодули, пока путь не указан явно. Посторонний клон
  публичного репозитория завершается успешно.
- `shallow = true` — при явной инициализации клонируется только история
  глубины 1. Брендбук и сайт не нужны как полная git-история внутри продукта.

В индексе git это gitlink (режим `160000`): указатель на конкретный коммит
смежного репозитория, а не содержимое файлов. `git submodule add` в этой
ветке отработал фактически, gitlink записан.

## 3. Компромисс публичного репозитория и приватных сабмодулей

| Требование | Обычный сабмодуль | Выбранная схема |
|---|---|---|
| Внешний `git clone --recurse-submodules` | Падает: нет доступа к private | Проходит: `update = none` не тянет сабмодули |
| Мейнтейнер с доступом | Получает деревья автоматически | Получает их явной командой `git submodule update --init vendor/<name>` |
| Утечка приватного содержимого | Риск, если рекурсивный клон «для всех» | Приватные деревья не клонируются посторонним |
| Ссылка в публичном репо | Рабочая только для своих | HTTPS-URL виден всем, содержимое — нет |

Итог компромисса: публичный репозиторий честно объявляет, что смежные
деревья существуют и где они живут, но **не пытается** скачать их от имени
анонимного клона. Посторонний видит `.gitmodules` и gitlink, не видит
брендбук, кабинет и биллинг. Мейнтейнер, у которого есть доступ к
`rox-one/rox-one-assets` и `rox-one/rox-one-website`, дотягивает деревья
отдельно.

Это не идеальная инкапсуляция (имена приватных репозиториев публичны), но
это единственный способ держать gitlink в публичном дереве без поломки
внешнего clone.

## 4. Как инициализировать сабмодули

Обычный клон публичного репозитория — без рекурсии, ничего дополнительного:

```bash
git clone https://github.com/rox-one/rox-one.git
cd rox-one
```

`git clone --recurse-submodules` тоже не должен падать: из‑за `update = none`
git не будет ходить за приватными URL.

Мейнтейнер с правом на приватные репозитории инициализирует **явно по пути**
(именно путь снимает `update = none` для этого вызова):

```bash
git submodule update --init vendor/rox-one-assets
git submodule update --init vendor/rox-one-website
```

Обе команды сразу:

```bash
git submodule update --init vendor/rox-one-assets vendor/rox-one-website
```

Нужна аутентификация GitHub (SSH-ключ, `gh auth`, или HTTPS с токеном).
Токен не записывается в `.gitmodules`. Пример одноразового helper:

```bash
export GH_TOKEN="…"   # fine-grained / PAT с доступом к rox-one-assets и rox-one-website
git -c credential.helper= \
    -c credential.helper='!f() { echo username=x-access-token; echo password='"$GH_TOKEN"'; }; f' \
    submodule update --init vendor/rox-one-assets vendor/rox-one-website
```

Повторно добавлять сабмодуль не нужно: `git submodule add` уже создал
записи и gitlink. Если на какой‑то машине в индексе нет gitlink (режим
`160000` на `vendor/rox-one-assets` и `vendor/rox-one-website`), это
ручной шаг восстановления:

```bash
git submodule add --depth 1 https://github.com/rox-one/rox-one-assets.git vendor/rox-one-assets
git submodule add --depth 1 https://github.com/rox-one/rox-one-website.git vendor/rox-one-website
```

После `add` снова выставить в `.gitmodules` `update = none` и `shallow = true`,
если git их затёр.

Проверка, что gitlink на месте:

```bash
git ls-files -s vendor/rox-one-assets vendor/rox-one-website
```

Ожидается режим `160000` и SHA коммита, не обычный каталог файлов.

## 5. Как запускать валидатор

Скрипт: `scripts/rx-validate.ts` (`RX-TSK-0701`, пайплайн `RX-PIP-0200`).

```bash
bun run scripts/rx-validate.ts
bun run rx:validate
```

Новых зависимостей у скрипта нет. YAML читается через `Bun.YAML.parse`.

Что проверяется:

1. `registry/rx-registry.yaml` и `registry/fragments/*.yaml` парсятся.
   Нет файла реестра или нет каталога фрагментов — это нормально, не ошибка.
2. Каждый `id` соответствует регулярному выражению из `registry/RX-LEGEND.md`.
3. Идентификаторы уникальны глобально (реестр + все фрагменты). Дубликат — ошибка.
4. `status` ∈ `planned` | `active` | `blocked` | `done` | `dropped`.
5. Все `refs` указывают на существующие `id`. Висячая ссылка — ошибка.
6. Каждый `docs/ru/RX-DOC-*.md` имеет YAML front matter `rx-id`, совпадающий
   с кодом в имени файла.
7. Если у записи есть `path`, путь должен существовать. Иначе — предупреждение,
   не ошибка.

Код выхода `1` — только при ошибках. Предупреждения сами по себе нулевой
код не меняют. Скрипт не бросает стек на отсутствие данных: внутренняя
ошибка печатается одной строкой и тоже даёт код `1`.

## 6. Как читать отчёт

Отчёт — человекочитаемый, на русском, в stdout.

```
=== Валидатор идентификаторов RX-* ===

Файлов реестра:  3
Записей:         42
Документов:      8

Ошибки (2):
  1. registry/fragments/foo.yaml#3: дубликат идентификатора RX-TSK-0001 (уже объявлен в …)
  2. registry/fragments/foo.yaml#4 (RX-TSK-0002): висячая ссылка RX-DOC-9999 — идентификатор не найден в реестре

Предупреждения (1):
  1. registry/fragments/foo.yaml#5 (RX-TSK-0003): путь «missing/path» не существует

Итог: 2 ошибки, 1 предупреждение.
Проверка не пройдена.
```

Как читать поля:

- **Файлов реестра** — сколько YAML-файлов удалось открыть (основной реестр
  плюс фрагменты). Ноль файлов — допустимо, пока соседние агенты не записали
  реестр.
- **Записей** — сколько объектов прошло базовый разбор (у них есть
  канонический `id`). Сломанные строки в отчёт ошибок попадают отдельно.
- **Документов** — сколько файлов `docs/ru/RX-DOC-*.md` просмотрено.
- **Ошибки** — блокеры: грамматика, дубликаты, чужой status, висячие `refs`,
  неразобранный YAML, несовпадение `rx-id` с именем документа.
- **Предупреждения** — мягкие сигналы. Сейчас это отсутствующий `path`.
  Их можно чинить отдельно; CI по `rx:validate` из‑за них не краснеет.
- **Итог / Проверка пройдена** — суммарный вердикт. Нулевой код выхода
  только если список ошибок пуст.

Типичные формулировки ошибок:

| Фрагмент сообщения | Что чинить |
|---|---|
| не соответствует грамматике | Опечатка в `RX-<DOMAIN>-<NNNN>`; домен должен быть из таблицы легенды |
| дубликат идентификатора | Один и тот же код в двух фрагментах или в реестре и фрагменте |
| status «…» не входит в словарь | Только пять английских ключей, без перевода |
| висячая ссылка | `refs` указывает на код, которого нет ни в реестре, ни во фрагментах |
| нет YAML front matter / rx-id не совпадает | В `docs/ru/RX-DOC-NNNN-*.md` нужен `rx-id: RX-DOC-NNNN` |
| не удалось разобрать YAML | Синтаксис файла; валидатор этот файл пропускает и продолжает остальные |

Пока фрагменты и `registry/rx-registry.yaml` пишутся параллельно, валидатор
может честно ругаться на висячие ссылки между ещё не созданными записями.
Это ошибка данных, а не падение скрипта.
