# Передача сентябрьской программы Rox

## Назначение и статус

Этот handoff передаёт проверенный снимок состояния репозиториев, ссылки на существующие программы и ограничения источников для продолжения аудита/спецификаций. Он **не** заявляет, что задачи реализованы, UI принят, E3/GG пройдены, облачные исполнители запущены или публикация выполнена.

Сводка исходного аудита: 79 человеческих запросов и 22 записи widget-response за seq1–1384; 30 подтверждённых групп U01–U31 плюс отдельная неоднозначность U25. Это группы, а не полный список требований. Исходные координаты `seqNNN` — ключи трассировки, не GitHub issue IDs. См. локальные `repository-state.json`, `attachment-manifest.json` и существующие источники аудита в экспорте; они содержат сведения о доказательствах, а не разрешение на изменение реализации.

## Репозитории и актуальная опора

- Исследуемый текущий код Rox — checkout `rox-one-september-program`, ветка `docs/september-program-20260930`, HEAD `f63294ba4fffa7238b46b24e918925a313ad0b12`. Эта ревизия является исходным якорем аудита, но не доказательством работающего приложения или прохождения приёмки.
- Найдено 51 checkout/worktree Rox, включая основной checkout, назначенный checkout и task worktrees. Их фактические HEAD/ветки/status и refs сохранены в отдельном registry состояния. Некоторые ветки detached, опережают/отстают от upstream, имеют удалённый upstream или локальные staged/unstaged изменения. Не переключать, не чистить и не переиспользовать их без проверки текущего владельца и свежего `git status`.
- В основном checkout на момент снимка были локальные изменения CSS и основная ветка отставала от `origin/main`; это отдельное состояние, не основание менять ветки или «синхронизировать» их в этой работе.
- Conation, Runfusion/Russian и Macro integration — отдельные checkout-проекты/доноры, а не доказательство реализации в Rox. Снимок не объединял их с Rox и не переносил код.

## Приоритетные границы доказательств

1. Исторический backlog служит источником намерения и остаточных требований; сообщения бота «готово» не заменяют свежую проверку кода, экрана, провайдера или поставки.
2. В текущем Rox уже есть source-level реализации ряда вещей, которые поздний исторический аудит называет незавершёнными. В частности, текущий якорь включает часть недавних изменений бренда/навигации/onboarding. Поэтому новые issues должны фиксировать конкретную проверочную дыру или остаточное поведение, а не утверждать, что всё соответствующее направление отсутствует.
3. Последние требования имеют приоритет: Inter; компактная иконная навигация и верхняя навигация по экранам; прозрачный `rox copy.png`; onboarding с одним именем и Rox defaults. Проверить каждое на актуальном коде и живом пользовательском сценарии, не возвращать устаревшие Arial Narrow/развёрнутый sidebar.
4. U25 — конфликтующая provenance widget-запись. Она не является полномочием менять defaults. Сохранить фактическое поведение до подтверждённого решения.
5. Не добавлять как пользовательские требования bot-added Zed importer, Liquid Glass, key rotation или карантинное удаление. Локальный Stalwart `@rox.one` — отдельный Mac-сценарий; production MX/DNS не менять автоматически. Встречный Whisper не отвечает на вопрос о модели voice input сессии; запрос с микрофона не означает разрешение автоматически захватывать system audio.
6. Полный аудит настроек охватывает 22 страницы и все запрошенные экраны; не сводить матрицу к нескольким основным маршрутам. В исходной Golden Gate приёмке есть противоречие 10 vs 12 локалей — сначала согласовать источник истины.

## Macro/Conation-переиспользование

Пакет Macro — спецификация и источник проверенных domain concepts, не автоматическое основание для копирования чужой реализации. Держать идентичности Rox-данных, authorization и provenance; не заводить вторую систему пользователей/сущностей/уведомлений. Для Conation U26 приёмка должна отдельно доказать JWT-authenticated populated data в Inbox, Drive, Mail, Chat, Tasks, Agents и CRM; Health 200 или unauthenticated 401 недостаточны. Сохранять весь исходный чек-лист onboarding, auth/OTP, E2E, Tauri/Mac, Dashboard, Inbox, Drive, Mail, Chat, Tasks, Agents, Notes/Canvas, прочих экранов, motion/typography и unresolved operational conditions. Эти требования не означают, что их надо заново реализовать в Rox.

## Передача изменённых файлов без потери состояния

- `repository-state.json` содержит read-only Git snapshot; в нём нет сырых remote URLs. Сверенные sanitized GitHub clone identities (без userinfo/query): Rox/RMA/Golden Gate и Macro→Rox — `https://github.com/rox-one/rox-one`; Conation fork — `https://github.com/agisota/conation`; Runfusion/Russian — `https://github.com/agisota/2026-09-23-2026-09-23-runfusion-rus`. Это идентичность remote, а не доказательство актуальности локально закэшированных refs.
- В private packet сохранены staged/unstaged бинарные патчи с хешами, подходящие untracked originals и incremental Git bundle. Два пути, сначала пропущенные из-за имени файла, проверены по содержимому: `SessionManager.ts` добавляет accessor просматриваемой сессии; `BottomTerminalDock.tsx` убирает hover-стиль. В этих diff нет credential material; полные staged/unstaged патчи теперь сохранены приватно. Не публиковать пакет и не добавлять его к issues.
- `private-packet/history/rox-one-incremental.bundle` сохраняет 162 локальных Rox commits, не достижимых из pinned 635 live origin heads; при создании было 92 local branches, в bundle — 74 refs, проверка bundle прошла. Macro→Rox использует ту же Git common directory и покрыт bundle. Для Conation и Runfusion по зафиксированным live refs не найдено local-only commits. Точные `git ls-remote --heads origin` ref snapshots и их hashes хранятся в private `history/live-origin-heads-*.txt`; Rox — 2026-09-30 00:40:33Z, Conation/Runfusion — 00:36:57Z. Branch reachability сверялась с этими сохранёнными OID; fetch не выполнялся. Bundle digest, 50 требуемых bases, ограничения сверки и восстановление указаны в `private-packet/history/history-manifest.json`.
- Для безопасного восстановления создать отдельный изолированный clone Rox, сверить текущие origin refs с требуемыми bundle bases и импортировать refs, не двигая существующие ветки/worktrees; сравнить каждый ref с ожидаемым OID. Staged/unstaged patches и подходящие untracked files накладывать только после сверки текущего содержимого и status. Чистый GitHub clone сам по себе не сохраняет dirty overlays, ignored state или локальные assets. Не выполнять reset, overwrite или принудительное перемещение существующего checkout на старый tip.
- Ignored-файлы, environment secrets, API credentials, keychain material, cookies, private event traces и полное содержимое home не копировались намеренно. Для bundle просмотрены 162 local-only commits / 493 изменённых пути: auth/credential-named paths относятся к source/tests, token/password assignments классифицированы как code expressions; signature-проверки private-key/GitHub/AWS token patterns совпадений не дали. Специализированного secret scanner в системе не оказалось. Это не гарантия отсутствия произвольного credential text во всех Git blobs. Raw original archive остаётся приватным.
- Приватный `attachment-manifest.json` перечисляет все 40 исходных metadata-записей; для двух локальных кандидатов SHA-256 совпадает с digest в metadata path (seq1257 и seq1360), остальные 38 binary недоступны либо не имеют независимого доказательства. Пути `.rox/attachments` и `Projects/Downloads` отсутствовали; удалось найти и приватно сохранить digest-match для seq1257. Проектный glob завершился по таймауту и не считается исчерпывающим. Отдельно недоступны seq1367 (mini-mode capsule reference) и seq1372–1376 (UI/settings references). Для seq1360 экспорт не содержал binary: логотип-кандидат совпадает с digest metadata, но его нельзя независимо сравнить с source bytes. В public repository и handoff нет personal screenshot binaries.
- Отдельно, уже после экспорта, пользователь приложил два новых OKR-референса. Их точные PNG bytes, размеры и SHA-256 сохранены приватно в `latest-okr-references/manifest.json`; они не входят в 40 исторических записей и не меняют статус 38 отсутствующих старых binaries. Новое требование `latest-user:OKR` отражено в [requirements-addendum.json](requirements-addendum.json), `OKR-01` и `OKR-02`.

## Проверяемый план продолжения

1. Перед каждым чтением/редактированием снова снять `HEAD`, branch, upstream и `git status` нужного checkout; сопоставить с `repository-state.json`. Не использовать устаревший дифф при изменившемся файле.
2. Сверить все claims источников с текущими entry points и существующими issue bodies; разделять `requested`, `verification-gap`, `proposal-audit` и `decision-reconciliation`. Для неизвестных API/UI границ сначала исследовать код, не придумывать имена handlers или публичные API.
3. Не переносить Macro implementation; взять нужные control contracts, провести rights review, назначить единичного владельца каждому shared file/root и явно согласовать prerequisites.
4. Для каждого продуктового остатка проверить минимум: пользовательский happy path; empty/loading/error/retry; авторизацию и изоляцию; persistence после reload; relevant concurrent/conflict/recovery; соседнюю регрессию; реальную native/browser/provider границу. Зафиксировать точный commit, окружение, действие, ожидаемый и наблюдаемый результат и артефакт. Не считать тест написанным, smoke успешным или provider принятым без такого свидетельства.
5. Для RMA отдельно запустить оригинальные E3 критерии, а не экстраполировать из harness; для Golden Gate разрешить locale-count contradiction и собрать требуемые visual/native/performance/packaging evidence. Сохранить открытыми те части, где среда/учётная запись/провайдер блокируют приёмку.
6. После проверки требований назначить владельцев, последовательные границы общих файлов и зависимости; повторно использовать реальные GitHub issues и Macro/RMA/GG программы, не изобретать номера или дубли.
7. На этом этапе сборки, тесты, линтеры, formatter, publication и application changes намеренно не запускались/не выполнялись. Интеграционный владелец должен проверить только после слияния всех авторских артефактов; данный handoff не объявляет какие-либо gates пройденными.

## Ограничения

Снимок отражает локальное состояние только в интервале, указанном в registry; checkout мог измениться после него. Экспорт подтверждает сохранённые тексты и метаданные, но не восстанавливает отсутствующий attachment binary или скрытые/удалённые записи. Установленное приложение, текущий UI, реальные account/provider paths и deployment не были перепроверены в рамках передачи.
