# Передача сентябрьской программы Rox

## Назначение и статус

Этот handoff передаёт проверенный снимок состояния репозиториев, ссылки на существующие программы и ограничения источников для продолжения аудита/спецификаций. Пакет документов опубликован и проверен: все 109 issues созданы, а точное удалённое содержимое и dependency links сверены (`PUBLISHED_VERIFIED`; [PROGRAM-01 · #1157](https://github.com/rox-one/rox-one/issues/1157)). Это не означает, что задачи реализованы, UI принят, E3/GG пройдены, облачные исполнители запущены или продукт проверен: поведение продукта `NOT STARTED`, задачи `NOT RUN`.

Сводка исходного аудита: 79 человеческих запросов и 22 записи widget-response за seq1–1384; 30 подтверждённых групп U01–U31 плюс отдельная неоднозначность U25. Это группы, а не полный список требований. Исходные координаты `seqNNN` — ключи трассировки, не GitHub issue IDs. Исходные тексты и доказательные материалы остаются приватными; публичный handoff содержит только безопасные выводы и координаты, а не raw source.

## Приоритетные границы доказательств

1. Исторический backlog служит источником намерения и остаточных требований; сообщения бота «готово» не заменяют свежую проверку кода, экрана, провайдера или поставки.
2. В текущем Rox уже есть source-level реализации ряда вещей, которые поздний исторический аудит называет незавершёнными. В частности, текущий якорь включает часть недавних изменений бренда/навигации/onboarding. Поэтому новые issues должны фиксировать конкретную проверочную дыру или остаточное поведение, а не утверждать, что всё соответствующее направление отсутствует.
3. Последние требования имеют приоритет: Inter; компактная иконная навигация и верхняя навигация по экранам; прозрачный `rox copy.png`; onboarding с одним именем и Rox defaults. Проверить каждое на актуальном коде и живом пользовательском сценарии, не возвращать устаревшие Arial Narrow/развёрнутый sidebar.
4. U25 — конфликтующая provenance widget-запись. Она не является полномочием менять defaults. Сохранить фактическое поведение до подтверждённого решения.
5. Не добавлять как пользовательские требования bot-added Zed importer, Liquid Glass, key rotation или карантинное удаление. Локальный Stalwart `@rox.one` — отдельный Mac-сценарий; production MX/DNS не менять автоматически. Встречный Whisper не отвечает на вопрос о модели voice input сессии; запрос с микрофона не означает разрешение автоматически захватывать system audio.
6. Полный аудит настроек охватывает 22 страницы и все запрошенные экраны; не сводить матрицу к нескольким основным маршрутам. В исходной Golden Gate приёмке есть противоречие 10 vs 12 локалей — сначала согласовать источник истины.

## Macro/Conation-переиспользование

Пакет Macro — спецификация и источник проверенных domain concepts, не автоматическое основание для копирования чужой реализации. Держать идентичности Rox-данных, authorization и provenance; не заводить вторую систему пользователей/сущностей/уведомлений. Для Conation U26 приёмка должна отдельно доказать JWT-authenticated populated data в Inbox, Drive, Mail, Chat, Tasks, Agents и CRM; Health 200 или unauthenticated 401 недостаточны. Сохранять весь исходный чек-лист onboarding, auth/OTP, E2E, Tauri/Mac, Dashboard, Inbox, Drive, Mail, Chat, Tasks, Agents, Notes/Canvas, прочих экранов, motion/typography и unresolved operational conditions. Эти требования не означают, что их надо заново реализовать в Rox.

## Проверяемый план продолжения

1. Before each read/edit, capture current `HEAD`, branch, upstream and `git status` for the relevant checkout; compare against the recorded snapshot. Do not rely on a stale diff if files have changed.
2. Сверить все claims источников с текущими entry points и существующими issue bodies; разделять `requested`, `verification-gap`, `proposal-audit` и `decision-reconciliation`. Для неизвестных API/UI границ сначала исследовать код, не придумывать имена handlers или публичные API.
3. Не переносить Macro implementation; взять нужные control contracts, провести rights review, назначить единичного владельца каждому shared file/root и явно согласовать prerequisites.
4. Для каждого продуктового остатка проверить минимум: пользовательский happy path; empty/loading/error/retry; авторизацию и изоляцию; persistence после reload; relevant concurrent/conflict/recovery; соседнюю регрессию; реальную native/browser/provider границу. Зафиксировать точный commit, окружение, действие, ожидаемый и наблюдаемый результат и артефакт. Не считать тест написанным, smoke успешным или provider принятым без такого свидетельства.
5. Для RMA отдельно запустить оригинальные E3 критерии, а не экстраполировать из harness; для Golden Gate разрешить locale-count contradiction и собрать требуемые visual/native/performance/packaging evidence. Сохранить открытыми те части, где среда/учётная запись/провайдер блокируют приёмку.
6. После проверки требований назначить владельцев, последовательные границы общих файлов и зависимости; повторно использовать реальные GitHub issues и Macro/RMA/GG программы, не изобретать номера или дубли.
7. Issue publication is `PUBLISHED_VERIFIED`: publisher сверил удалённые titles, bodies, labels и dependency links всех 109 issues; дополнительных issues при сверке не создавалось. Product behavior остаётся `NOT STARTED`, все задачи — `NOT RUN`. В этой передаче сборки, продуктовые тесты, линтеры, formatter и application changes не запускались/не выполнялись; данный handoff не объявляет продуктовые gates пройденными.

## Ограничения

Снимок отражает локальное состояние только в интервале, указанном в registry; checkout мог измениться после него. Экспорт подтверждает сохранённые тексты и метаданные, но не восстанавливает отсутствующий attachment binary или скрытые/удалённые записи. Установленное приложение, текущий UI, реальные account/provider paths и deployment не были перепроверены в рамках передачи.
