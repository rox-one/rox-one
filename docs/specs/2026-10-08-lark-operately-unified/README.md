# Rox Unified Suite: единая спецификация (Lark + Operately поверх Rox)

**Версия:** unified **v2** (включая v2.1), 08.10.2026 (MSK) (v1 сохранена в `v1/`) · **Владелец:** Mark Lindgreen · **База кода (только чтение):** `rox-one/rox-one` @ `aedff592`

## Что изменилось в v2

Ревизия по брифу Марка (пункты A–F). Все документы обновлены на месте. Предыдущая версия лежит в `v1/`.

- **A. Транскрипт omp.** `inputs/omp-session-transcript.json` разобран через Python json как данные, а не инструкции. Результат — `inputs/omp-session-requirements.md`: 27 пунктов с цитатами.
  - Принято 17, частично 1, не принято 9; по каждому указано где и почему.
  - Главный вывод: сессия была про UI-паритет с super.engineering, а не про эту спецификацию. Поэтому перенесены только общие правила: профили UI без форка, State · Composition · Motion · Transitions для каждого экрана, негативные и визуальные проверки, справка с формулами, standing approvals, readback перед «готово», ничего в `~/Documents` и `~/Desktop`.
  - Инфраструктурные детали из системного промпта (IP, почты, пути к токенам) намеренно не воспроизводятся.
- **B. Все файлы Rox — в `~/rox`, а не в `~/.rox`.**
  - ADR-U13, модуль M23, пакет W1-13, миграция MIG-13, TECH-SPEC §10.
  - Сейчас в коде есть обе папки: `~/rox` берётся, только если уже существует, иначе `~/.rox`. В 22 файлах `.rox` захардкожен; их полный список и замены — в TECH-SPEC §10.2.
  - Миграция переносит данные и оставляет `~/.rox` симлинком, ничего не удаляет; есть `--revert`.
- **C. Совместная работа и создание из любого места.**
  - Совместная работа (M18, UI-SPEC §18, TECH-SPEC §11): присутствие, Yjs-курсоры и follow mode, треды комментариев с упоминаниями, **режим предложений** (MIT-библиотека вместо платного TipTap Pro), диалог «Поделиться», офлайн и конфликты, отметки о прочтении, общие списки задач и календари.
  - Создание задач, встреч и событий из документов и чата (M19, UI-SPEC §19, TECH-SPEC §12): inline-блоки, slash-команды, выделение → задача, сообщение → задача / событие / документ, `/group`. Для каждого действия есть контракт команды.
- **D. Автономия агента `@rox`** (ADR-U14, M20, UI-SPEC §22, TECH-SPEC §13). У каждого участника свой агент, который работает в существующем runtime omp (второго оркестратора нет).
  - Действует только через ту же шину команд.
  - Права: scopes ∩ ACL владельца.
  - Классы риска: обычные выполняются сами, заметные другим и привилегированные — после подтверждения.
  - Постоянные разрешения, лимиты частоты, аварийная пауза, журнал аудита с хеш-цепочкой.
- **E. Встроенные автоматизации R1–R5** (ADR-U15, DATA-MODEL §5.16, TECH-SPEC §14). У каждой есть ключ идемпотентности.
  - R1: событие → заметки встречи, привязанные к дню и дневной заметке, плюс черновик задачи в «Бэклоге».
  - R2: новый участник → общий чат команды и личный агент.
  - R3: новый аккаунт → DM с `@rox` и приветствием.
  - R4: приглашения по email → неактивированные участники-плейсхолдеры в чате команды; история сохраняется после регистрации.
  - R5: личный Диск на 1 ТБ (экраны в UI-SPEC §20, бэкенд SeaweedFS, учёт квоты, артефакты агентов в виртуальных папках).
- **F. Исследован macro-inc/macro** (лицензия **AGPL-3.0**, только чтение, код не копировался). Механизм приветствия описан в TECH-SPEC §17 и адаптирован как clean-room.
  - Вебхук создания пользователя запускает фоновые задачи: стартовые документы и системный канал.
  - Сотрудник постит приветствие через обычные команды с политикой «уведомлять только упомянутых».
  - Упоминания хранятся как теги с JSON.
  - Отличие от брифа: Macro не перечисляет @handles ботов. В Rox приветствие перечисляет только реально резолвящиеся handles.
- **Решения v2 D-v2-1…D-v2-13 утверждены Марком 08.10.2026** («ВСЁ ОК»; PRD §11.1), сводка ниже. Тогда же утверждены заведение задач по плану и PR со спецификацией.

## Коротко

Это один документ-пакет, который переносит **все поверхности Lark** (Messenger, Docs/Wiki/Drive, Tasks, Calendar, Meetings, Contacts, OKR, Base/Forms, Workplace, Mail) и **все поверхности Operately** (цели, проекты, таргеты, чек-листы, дерево подцелей и проектов, чек-ины, обсуждения, вехи, ресурсы, champion/reviewer/contributors, приватность, close/move/delete, Work Map, Review, Spaces, KPI) на то, что в Rox **уже есть**. Параллельных копий не создаём.

Главные принципы:
- **Одна модель сущностей.** 54 вида сущностей (21 существующий в Rox + 33 новых, включая `invitation` из v2) адресуются как `kind:id`. Связи хранятся в одной таблице `entity_link` (12 типов). Ссылки имеют вид `rox://…`. Карточки рисует единый реестр resolver/preview. Универсальной «базы всех сущностей» нет (ограничение аудита §9).
- **Любая поверхность ссылается на любую сущность.** Из чата можно создать задачу, документ, встречу, цель, проект, веху, чек-ин или KPI-запись: 17 slash-команд и меню «⊕ Создать». В v2 добавлены `/group`, `/call`, `/drive`, slash-команды в документах и вызов `@rox`.
- **Заметки = Lark Docs.** Личные заметки остаются Markdown-файлами. Общий доступ включается явной миграцией (#1112) в серверный документ с Yjs; сервер пишет снимки обратно в Markdown. У документа всегда ровно один «хозяин» (authority).
- **Задачи.** PersonalTask (Things) расширяется до WorkItem v3. Lark Tasks и формат задач Operately (статусы, приоритет, размер, вехи, доски) — это **представления над одним хранилищем**. Личные задачи остаются local-first, общие реплицируются в workspace-service через команды и outbox.
- **Цели.** Проектный OKR превращается в дерево целей уровня организации, пространства и личных целей (= цели Operately = Objectives Lark). Таргеты = KR. Одна таблица чек-инов и одна таблица ревью.
- **Messenger** — новый режим (rail, order 25). AI-сессии остаются в Chat и связываются с сообщениями перекрёстными ссылками.
- **Все новые флаги по умолчанию ВЫКЛЮЧЕНЫ.** Изменения идут через версионированные команды. TipTap остаётся единственным редактором. Не появляются: режим «Timeline», второй оркестратор, хост Cordis. Поддерживаются 12 локалей, RU по умолчанию.

### Решения v2 — ✅ УТВЕРЖДЕНЫ Марком 08.10.2026 (PRD §11.1)
- **D-v2-1.** Переносим `~/.rox` → `~/rox` и оставляем симлинк, ничего не удаляем. Конфликт с прежней директивой «живые dot-конфиги не переносить» (пункт #14 транскрипта) решён в пользу требования B.

- **D-v2-6.** Классы риска по умолчанию: обычные — автоматически, заметные другим и привилегированные — с подтверждением. Приглашение людей всегда привилегированное.
