## 1. Контекст и назначение

ROX — локальное-first приложение (Electron + локальный сервер, RU-first), в котором уже есть фундамент для работы с кодом
и знаниями, но он разрознен и не образует продуктовой поверхности: code-intelligence даёт снапшоты и провенанс, но
показывается лишь панелью внутри `pages/ProjectRoadmapPage.tsx` (`components/code-intelligence/RepositorySnapshotPanel.tsx`);
индексация источников (`packages/server-core/src/sources/source-index.ts`), vault-индекс Notes
(`packages/server-core/src/knowledge/vault-index.ts`), markdown-пайплайн `content:*` и голосовой слой
(`packages/shared/src/voice/*`) существуют порознь. Пользователь не может «вставить ссылку на репозиторий и получить
понятное пространство»: нет каталога репо, нет автоматического пайплайна анализа с прогрессом, нет единого репо-воркспейса
с вики, графами, схемами, вопросами и турами, а ноутбуков-поверхности для знаний и подкастов нет вовсе.

Поэтому продукт добавляет две новые поверхности. **Developer Space** — верхнеуровневый пункт «Разработчикам» с каталогом
репозиториев и репо-воркспейсом: подключение репо → автоматический анализ → шесть артефактов (wiki, понимание, граф кода,
схемы, knowledge-graph, C4/OKF), три блока сгенерированных вопросов, визуальные туры в «демо-режиме» и свободный чат.
**ROX Playbooks** — ноутбук-поверхность с режимом **знаний** (загрузка источников → пресет-вопросы → подкаст в один клик)
и режимом **кодбука** (ноутбуки-пайплайны по коду). Обе поверхности читаются агентами через session-tools с разными
уровнями ответственности и учитывают свежесть репозитория (freshness/drift). Гейтинг — онбординг-роль «разработчик» (D1),
эгресс — по гранулярному per-repo согласию (D6).

## 2. Цели и метрики успеха

| Цель | Изменение (что должно стать иначе) | Как проверяем |
|---|---|---|
| C1. Репо подключается без терминала | Пользователь вставляет ссылку на репозиторий в UI и получает клон в управляемое пространство `projects/<slug>` (D3) | Приёмочный кейс: вставить HTTPS-ссылку → репо появляется в каталоге; для приватного — GitHub device-login (FR-016) |
| C2. Анализ даёт обозримый прогресс, а не «тишину» | Запуск анализа показывает этапы и «шаг N из M», допускает отмену и возобновление (D5) | Ручной прогон: на живом репо виден прогресс по этапам; отмена в середине → повторный запуск доходит до конца |
| C3. Всё ключевое предрендерено | Скелет артефактов виден сразу, LLM-слой (wiki/понимание/вопросы) доезжает фоном (D5, D8) | UI-тест: сразу после старта видны каркасы поверхностей; наполнение появляется по мере готовности |
| C4. Вопросы несут ценность и объяснимы | По 10 вопросов на каждый из трёх блоков; клик открывает тур или текст; есть пометка «почему этот вопрос» (D8) | Проверка контента: 3 блока × 10 вопросов; у каждого — причина персонализации |
| C5. Туры объясняют репо наглядно | Динамические туры генерируются из артефактов; демо-режим с виньеткой и прогрессом; reduced-motion уважается (D9, D10) | Прогон тура: виньетка + «шаг N/M» + пауза/выход; при `prefers-reduced-motion` — статика |
| C6. Знания превращаются в подкаст за минуты | Источники → пресет-вопросы → двухголосый подкаст с плеером и экспортом `mp3`/`srt` (D12, D13) | Сквозной сценарий: загрузить 1 источник → нажать «подкаст» → получить плеер и скачать файл |
| C7. Приватность под контролем пользователя | Эгресс только по per-repo согласию; аудит-лог; дефолтные исключения секретов (D6) | Тест: без согласия сетевых вызовов нет; в логе — записи о согласии и о блокировках |
| C8. Ничего не ломаем в существующих ветках | Скип онбординг-шага безопасен; ветки `git-bash`/`rox-connect` целы (D1) | Прогон онбординга со скипом шага «Кто вы?» — существующие пути проходятся |
| C9. Локальность и доступность | Все новые строки — в 12 локалях; новые поверхности доступны с клавиатуры и SR (D14) | `lint:i18n:parity|sorted|coverage` зелёный; a11y-прогон новых экранов |

Формулировки метрик проверяются через `06-acceptance-cases.json` (машиночитаемая связка с FR) и DoD волн из `05-PLAN.md`.

## 3. Не-цели (осознанно не делаем в v1)

- **Авто-watch / авто-pull репозитория.** Обновление — ручной кнопкой + бейдж «устарело» (D3).
- **Авто-регенерация артефактов** при новом снапшоте без действия пользователя (D7).
- **Webui-версия** новых поверхностей — вне v1; приёмка только native macOS/Windows (D14, риск 9).
- **N-агентный подкаст** с произвольными ролями и голосами — v1.x; в v1 строго 2 голоса (D13).
- **Вендоринг SurfSense** как сайдкар-сервиса или форк его кода — только порт концепций (D12, риск 5).
- **DeepWiki-open как обязательный компонент** — не берём; wiki строит `openwiki` (D5).
- **Построение Playbooks на SiYuan-поверхности** — она жёстко выключена (`knowledgeEnabled=false`) (риск 7).
- **Автоматическое включение Developer Space «по сигналу»** (вставил ссылку, подключил git/CLI) — только напоминание (D1).
- **Молчаливый эгресс** (вызовы моделей/CVE/обновлений инструментов без согласия) — запрещён (D6).
- **Новые демоны/фоновые службы** для инструментов анализа — инструменты запускаются по операции (D4).
- **Новый движок туров** — расширяем существующий product-tour (D9).

## 4. Персоны и онбординг-гейт

### 4.1 Персоны

| Персона | Кто это | Что ей нужно от продукта | Гейт |
|---|---|---|---|
| **Разработчик** (основная) | Пишет/читает код, знакомится с чужим репо, готовит фичи | Быстро понять репо: wiki, граф, схемы, C4; вопросы-обучение; туры «где что лежит»; свой вопрос к репо | Developer Space **включён по умолчанию** |
| **Смежные роли** (аналитик/дизайнер/продакт/др.) | Работает рядом с кодом, но не автор | Иногда заглянуть в репо-объяснения; основной инструмент — Playbooks-знания | Developer Space **выключен**; включается вручную |
| **Не-разработчик, которому «всё-таки надо»** | Столкнулся с репо по задаче | Сам находит экран в Настройках → Разработчикам и включает | Ручное включение |
| **Владелец знаний** (любая роль) | Собирает материалы и хочет их «проговорить» | Playbooks-знания: источники → пресет-вопросы → подкаст | Не гейтится ролью |

### 4.2 Онбординг-гейт (D1)

- В мастер первого запуска добавляется шаг **«Кто вы?»** после шага имени. Существующая цепочка:
  `OnboardingWizard.tsx` (`OnboardingStep`, `renderStep()`), первый шаг `WelcomeStep.tsx` (имя) →
  `onboarding-username.ts` (`nextStepAfterUsername`, `persistOnboardingUsername`). Шаг «Кто вы?» встраивается
  между именем и следующим существующим шагом.
- Выбор: **разработчик — да/нет** + смежные роли (аналитик/дизайнер/продакт/др.).
- **Дефолты:** «разработчик» → Developer Space включён по умолчанию; все остальные (и скип) → выключен.
- **Путь ручного включения:** карточка «Разработчикам» живёт в Настройки → Разработчикам; пользователь включает сам.
- **Мягкие сигналы** (вставил ссылку на репо, подключил git/CLI) используются **только как напоминание**
  («включить экран разработчика?»), никогда как молчаливое автовключение.
- **Скип безопасен:** ветки онбординга `git-bash`, `rox-connect` не ломаются; отсутствие ответа трактуется как «не разработчик».
- **Net-new:** роли/профессии в онбординге сегодня нет, связки «ответ → дефолт фичи» нет — всё создаётся
  (карта фактов §3.1). Персистентность онбординг-ответов опирается на существующие `EnvironmentPrefs`/`QUESTION_IDS`
  (`packages/shared/src/environment/types.ts`, `storage.ts`) как расширение, а не второй механизм.

## 5. Точки входа и IA (D2)

- **Новый верхнеуровневый пункт «Разработчикам»** — nav destination с каталогом репозиториев → репо-пространство.
  Реализуется как новая запись в `nav-destinations.ts` (`APP_NAV_DESTINATIONS`; сегодня 17 записей, правило «add once»),
  потребляется `AppShell.tsx` (links[]) и `platform/ActivityRail.tsx` (rail groups), рендер — `MainContentPanel.tsx`.
- **Вторая точка входа:** та же реализация доступна вкладкой/диплинками из Проекта (одно ядро, две точки входа).
  Прошлое решение «только вкладка внутри Проектов» пересмотрено в пользу нового пункта (запрос пользователя, D2).
- **Каталог репо** — список подключённых репозиториев (карточки: имя, статус анализа, свежесть/бейдж «устарело», последний снапшот).
- **Репо-воркспейс** — единое пространство одного репо: шапка (репо, свежесть, кнопки «обновить»/«анализ»), шесть
  поверхностей-артефактов, три блока вопросов, туры/демо-режим, чат «свой вопрос».
- **Диплинки из Проекта:** карточка репо/панель в Проекте открывает тот же репо-воркспейс (по slug-репо), без дублирования логики.
- **Playbooks** — отдельная ноутбук-поверхность; старый видимый ярлык SessionWorkbench «playbook holes» переименовывается
  в «Веера задач» для устранения коллизии имени (D12).

## 6. Пользовательские сценарии

Формат: **триггер → шаги → результат**.

1. **Подключение репозитория.**
   *Триггер:* пользователь хочет проанализировать чужой/свой репо.
   *Шаги:* открыть «Разработчикам» → «Подключить репо» → вставить ссылку; для приватного — пройти GitHub device-login;
   либо привязать локальную папку как альтернативу.
   *Результат:* репо появляется в каталоге как репо-проект `projects/<slug>`; готово к запуску анализа.

2. **Первый анализ с прогрессом.**
   *Триггер:* репо подключён, пользователь нажимает «Анализировать».
   *Шаги:* запускается каскад — структурные артефакты сразу, LLM-слой фоном; пользователь наблюдает этапы и «шаг N из M»;
   при необходимости ставит на паузу/отменяет; при сбое — возобновляет.
   *Результат:* скелет шести поверхностей виден сразу, наполнение доезжает; отмена и возобновление работают без потери прогресса.

3. **Просмотр wiki.**
   *Триггер:* анализ завершён, пользователь открывает поверхность «Wiki».
   *Шаги:* читает связанные markdown-страницы с Mermaid-диаграммами и кросс-ссылками; переходит по ссылкам; видит провенанс.
   *Результат:* пользователь понимает структуру репо из репо-owned wiki (генератор `openwiki`), эталон UX — DeepWiki.

4. **Изучение схем/графов/C4.**
   *Триггер:* нужен структурный взгляд на код.
   *Шаги:* открывает «Граф кода» (символы/вызовы), «Схемы» (диаграммы), «Knowledge-graph», «C4/OKF».
   *Результат:* видит связи символов/вызовов, схемы, knowledge-graph и C4-архитектуру; каждый артефакт с провенансом.

5. **Прохождение тура по вопросу.**
   *Триггер:* пользователь кликает вопрос в блоке (развёрнутый ответ через тур).
   *Шаги:* запускается динамический тур в демо-режиме — виньетка, пульс целевого блока, «шаг N из M», пауза/выход.
   *Результат:* пользователь наглядно понимает ответ там, где он «живёт» на экранах; прогон персистится (IndexedDB).

6. **Свой вопрос в чате.**
   *Триггер:* готовая формулировка не покрыта блоками.
   *Шаги:* в композере под блоками пишет свой вопрос (пикер модели/коннекта, вложения); запрос уходит в обычную сессию,
   привязанную к репо.
   *Результат:* ответ в сессии, которая видна в списке сессий, продолжаема, инструменты доступны; при наличии — кнопка
   «Показать на экранах» запускает сгенерированный тур.

7. **Не-разработчик включает экран вручную.**
   *Триггер:* не-разработчик (или скипнувший шаг) видит напоминание «включить экран разработчика?».
   *Шаги:* переходит в Настройки → Разработчикам → включает Developer Space; либо прямо из напоминания.
   *Результат:* пункт «Разработчикам» и поверхность становятся доступны; автовключения не происходит.

8. **Playbooks-знания (источники → пресет-вопросы → подкаст).**
   *Триггер:* пользователь хочет освоить/пересказать материал.
   *Шаги:* загружает источники (документы/файлы) → пользуется пресет-вопросами и чатом с цитатами → нажимает «подкаст».
   *Результат:* получает сценарий и двухголосую озвучку с плеером; при желании скачивает `mp3`/`srt`.

9. **Кодбук.**
   *Триггер:* нужен воспроизводимый ноутбук-пайплайн по коду.
   *Шаги:* открывает Playbooks в режиме «кодбук», собирает ноутбук из шагов.
   *Результат:* готовый ноутбук-пайплайн, связанный с репо-артефактами (волна В5).

## 7. Функциональные требования

Каждое требование проверяемо; «как проверяем» — наблюдаемое действие/результат. Ссылки на существующий код — из брифа §3.

### A. Онбординг и гейтинг

- **FR-001.** Мастер первого запуска включает шаг «Кто вы?» после шага имени с выбором «разработчик: да/нет» и смежными
  ролями (аналитик/дизайнер/продакт/др.). *(новое; расширение `OnboardingWizard.tsx`, `WelcomeStep.tsx`, `onboarding-username.ts`)*
  *Как проверяем:* пройти первый запуск — шаг виден, после имени; выбор сохраняется.
- **FR-002.** Выбор «разработчик» → Developer Space включён по умолчанию; любой другой ответ и скип → выключен.
  *Как проверяем:* два прогона онбординга (да/скип) — состояние флага Developer Space после завершения совпадает с ожиданием.
- **FR-003.** Скип шага «Кто вы?» не ломает существующие ветки онбординга `git-bash` и `rox-connect`.
  *Как проверяем:* прогон онбординга со скипом — обе существующие ветки проходятся без ошибок.
- **FR-004.** Ответы онбординга хранятся в существующем механизме `EnvironmentPrefs`/`QUESTION_IDS`
  (`packages/shared/src/environment/types.ts`, `storage.ts`), а не через второй реестр.
  *Как проверяем:* после онбординга ответ читается из `EnvironmentPrefs`; дублирующего хранилища нет.
- **FR-005.** Мягкие сигналы (вставка ссылки на репо, подключение git/CLI) приводят **только** к напоминанию
  «включить экран разработчика?»; молчаливого автовключения нет.
  *Как проверяем:* при выключенном Developer Space вставить ссылку/подключить git — появляется напоминание; состояние флага не меняется само.

### B. Флаги и настройки

- **FR-006.** Developer Space гейтится флагом в существующей системе флагов
  (`packages/core/src/platform/workbench/flags.ts`, `WORKBENCH_FEATURE_FLAGS`) как **(расширение)** с `alwaysOn=false`.
  *Как проверяем:* при выключенном флаге пункт недоступен; при включённом — доступен.
- **FR-007.** Состояние флага Developer Space персистится тем же механизмом рендерер-атомов
  (`atoms/{mode-flags,extra-screens,unified-shell}.ts`, `lib/local-storage.ts`).
  *Как проверяем:* перезапуск приложения сохраняет выбранное состояние.
- **FR-008.** Страница настроек «Разработчикам» регистрируется в реестре настроек
  (`apps/electron/src/shared/settings-registry.ts` `SETTINGS_PAGES`, `pages/settings/settings-pages.ts` `SETTINGS_PAGE_COMPONENTS`,
  `shared/menu-schema.ts` `SETTINGS_ITEMS`) и использует существующий компонент-тумблер (`SettingsToggle` в
  `pages/settings/ExtraScreensSettings.tsx`, `WorkbenchChromeSettings.tsx`).
  *Как проверяем:* страница открывается из настроек и из меню; тумблер включает/выключает поверхность.
- **FR-009.** Пункт «Разработчикам» добавляется одной записью в `nav-destinations.ts` (`APP_NAV_DESTINATIONS`, правило
  «add once»); в потребителях `AppShell.tsx` и `ActivityRail.tsx` допустимы минимальные аддитивные изменения
  (регистрация пункта/флагов), поведение существующих пунктов не меняется.
  *Как проверяем:* пункт виден в rail/nav; существующие пункты работают как прежде, изменения потребителей — только аддитивные.
- **FR-010.** Настройки Developer Space включают минимум: вкл/выкл поверхности, дефолты онбординга, управление репо-каталогом.
  *Как проверяем:* все три группы настроек присутствуют и управляемы.

### C. Каталог и подключение репозитория

- **FR-011.** Каталог репо показывает подключённые репозитории карточками: имя, статус анализа, свежесть (в т.ч. бейдж
  «устарело»), последний снапшот.
  *Как проверяем:* при ≥1 репо карточка содержит все четыре поля; состояние «устарело» отображается по freshness.

## 8. Состояния (для новых поверхностей)

Общие требования к состояниям для каталога репо, репо-воркспейса, шести артефактов, блоков вопросов, Playbooks и подкаста.

| Состояние | Требование |
|---|---|
| **empty** | Осмысленный пустой экран с действием-призывом (подключить репо / загрузить источник); без «мёртвой» пустоты. |
| **loading** | Скелет/плейсхолдер поверхности виден сразу (каскад D5, D8); LLM-слой доезжает фоном без блокировки. |
| **error** | Понятное сообщение причины и действие восстановления (повторить/изменить ввод); не «голый» стек. |
| **partial** | Частичная готовность: доступные артефакты/вопросы показываются, недостающие помечены как «в работе/недоступно». |
| **offline** | Сетевые операции (CVE, обновления инструментов, клон, модельные коннекты) деградируют явно; локальные артефакты доступны. |
| **disabled** | Выключенная поверхность/функция (флаг, отсутствие согласия, нет `syft`) объясняет, почему недоступна, и как включить. |

Требования конкретизируются по экранам в `04-UI-SPEC.md`; проверяются через `06-acceptance-cases.json`.

## 9. Локализация и доступность

- Локализация: 12 локалей, RU — дефолт, ключи ASCII-sorted, гейты `lint:i18n:parity|sorted|coverage` (FR-061, FR-062).
- Доступность: клавиатурная навигация, доступные имена/роли, контраст по токенам, уважение `prefers-reduced-motion`
