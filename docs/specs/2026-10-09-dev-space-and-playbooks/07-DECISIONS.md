# 07-DECISIONS — журнал решений

Статус документа: **DRAFT для ревью**. Все решения ниже имеют статус
**принято 2026-10-09 (по рекомендации интервью)** — раунд-1 интервью, 14 вопросов, рекомендации приняты
полностью («делай всё как рекомендуешь»). См. `00-BRIEF.md` §2.

Формат: для каждого решения — контекст, выбранный вариант, отклонённые альтернативы и причины отказа,
последствия. Отклонённые альтернативы приведены только те, что зафиксированы брифом.

---

## D1. Онбординг-роль и дефолты

- **Контекст.** Мастер первого запуска (`OnboardingWizard.tsx`, `useOnboarding.ts`) не знает роли
  пользователя; связки «ответ → дефолт фичи» нет. Есть шаг имени (`WelcomeStep.tsx`,
  `onboarding-username.ts`) и существующие ветки `git-bash`, `rox-connect`.
- **Выбрано.** Новый шаг «Кто вы?» после имени: разработчик — да/нет + смежные роли
  (аналитик/дизайнер/продакт/др.). «Разработчик» → Developer Space включён по умолчанию; остальным —
  выключен, но карточка живёт в Настройки → Разработчикам. Мягкие сигналы (ссылка на репо, git/CLI) —
  только напоминание «включить экран разработчика?». Скип шага безопасен.
- **Отклонено.** Молчаливое автовключение по мягким сигналам — недопустимо как скрытое изменение
  поведения. Обязательность шага — ломала бы существующие ветки онбординга и скип.
- **Последствия.** Net-new типы `EnvironmentPrefs`/`QUESTION_IDS` (`environment/types.ts`, `storage.ts`);
  дефолт фичи Developer Space зависит от ответа; существующие ветки онбординга не ломаются.

## D2. Место Developer Space в навигации

- **Контекст.** Паттерн навигации — `nav-destinations.ts` (`APP_NAV_DESTINATIONS`, «add once»),
  потребители `AppShell.tsx`, `platform/ActivityRail.tsx`, рендер `MainContentPanel.tsx`.
- **Выбрано.** Новый верхнеуровневый пункт «Разработчикам» (rail/nav destination) с каталогом репо →
  репо-пространство; та же реализация доступна вкладкой/диплинками из Проекта (одно ядро, две точки входа).
- **Отклонено.** Прошлое дизайн-решение «только вкладка внутри Проектов» — пересмотрено в пользу нового
  пункта по запросу пользователя.
- **Последствия.** Запись в `APP_NAV_DESTINATIONS`; один общий shell-контракт на обе точки входа.

## D3. Ингест репозитория

- **Контекст.** `clone API` в GitHub-контуре нет (`workgraph:startGithubDeviceLogin|…`, токены в
  credential store, рендеру не отдаются); `shell:exec` ограничен 20 s и для длинных пайплайнов не годится.
- **Выбрано.** Клон по ссылке в управляемое пространство проектов (`projects/<slug>`); приватные
  репозитории — через существующий GitHub device-login; привязка локальной папки — как альтернатива.
  Актуализация — ручная кнопка «проверить свежесть/обновить» (паттерн freshness code-intelligence) +
  бейдж «устарело».
- **Отклонено.** Авто-watch/pull — не в v1.
- **Последствия.** Новый RPC-контур ингеста; GitHub-токен не выходит в рендер; место клона — TODO(open) O4.

## D4. Реестр инструментов: шесть, «одна операция — один инструмент»

- **Контекст.** Существующий контракт code-intelligence (`CI-DEC-EXTEND-EXISTING-01`,
  `REJECTED_CODE_INTEL_TOOLS` = CodeWiki/DeepWiki/Graphify/Archify) и реестр
  `capabilities/packs.ts`, где инструменты объявлены «available» с placeholder-репозиториями
  (`sourceRepo: example/*`) — гэп `CI-G-08 CURRENT_SOURCE_CONFLICT`.
- **Выбрано.** Шесть инструментов, каждому — своя операция: wiki = `langchain-ai/openwiki`;
  понимание/туры = `Egonex-AI/Understand-Anything`; граф кода = `codegraph`; схемы = `archify`;
  knowledge-graph = `graphify`; C4/OKF = `Groma.md`. Выпускается **новая ревизия решения** поверх
  `CI-DEC-EXTEND-EXISTING-01` с протоколом свежего аудита, правилом «без дублей», `alwaysOn=false`,
  **без демонов**.
- **Отклонено.** Старые rejection-причины «duplicate/unmaintained» — опровергнуты текущей активностью
  проектов. Дубли в реестре — запрещены правилом. Демоны — не запускаем.
- **Последствия.** Ревизия обязана согласовать `CI-G-08 CURRENT_SOURCE_CONFLICT`; финальный аудит может
  схлопнуть пересечение groma↔archify по диаграммам (TODO(open) O2); выбор канонического
  codegraph-провайдера — O1; финальные пины/лицензии — O7.

## D5. Генерация

- **Контекст.** Требование UX «всё предрендерить» против стоимости LLM.
- **Выбрано.** Основной генератор wiki/понимания — `openwiki` (локальный агентный CLI+MCP, репо-owned
  markdown, Mermaid, кросс-ссылки). Каскад: структурные артефакты (codegraph/groma/graphify/archify) —
  сразу локально при анализе; LLM-слой (wiki, «понимание», блоки вопросов) — фоном с прогрессом;
  UI показывает скелет сразу.
- **Отклонено.** `deepwiki-open` как обязательный компонент — не берём (отдельный веб-стек).
- **Последствия.** Двухфазная выдача (скелет → LLM-контент); LLM-фаза — фоновая джоба под per-repo
  согласием (D6).

## D6. Эгресс и приватность

- **Контекст.** Существующий гейт PREVIEW/BIND с `dataEgress:'deny'`; дефолтные исключения `.env*`,
  `**/*.pem`, `**/*.key`, `**/.codegraph/**`.
- **Выбрано.** Гранулярное per-repo согласие на: вызовы настроенных модельных коннектов, сеть для
  CVE-проверок (OSV) и обновлений инструментов. Дефолтные исключения сохраняются; аудит-лог; локальная
  модель — рабочая опция.
- **Отклонено.** Молчаливый эгресс — нет.
- **Последствия.** Каждый эгресс-путь проходит через согласие; аудит-лог обязателен.

## D7. Артефакты

- **Контекст.** Снапшоты code-intelligence хранятся в
  `projects/<slug>/code-intelligence/<bindingId>/<policyFingerprint>/snapshot_*.json` с provenance;
  публикация markdown — пайплайн `content:*`, Notes/vault-index.
- **Выбрано.** Источник правды — локальные артефакты в `projects/<slug>/dev-space/...` (JSON/MD/SVG),
  версионируемые, с provenance. Человекочитаемые страницы публикуются в Notes/Pages (markdown-пайплайн
  `content:*`, wikilinks, поиск vault-index). Агенты читают через session-tools (паттерн `knowledge_*`);
  запись — propose/approve. Обновление — кнопкой при новом снапшоте + бейдж «устарело».
- **Отклонено.** Авто-регенерация — не в v1.
- **Последствия.** Единый формат артефактов для всех шести инструментов; агентский доступ —
  read/propose/apply через session-tools.

## D8. Блоки вопросов

- **Контекст.** Нужны предгенерированные вопросы и развёрнутые ответы; SBOM/CVE требуют эгресса.
- **Выбрано.** Предгенерация при анализе: по **10 вопросов на блок** (обучение; фичи/улучшения;
  безопасность/зависимости/производительность), пересчёт при новом снапшоте; развёрнутые ответы — по
  клику (тур или текст); персонализация онбординг-профиль + репо-контекст + рабочие сигналы
  (незакоммиченное, CI) с пометкой «почему этот вопрос». В блоке 3 — SBOM (`syft`, optional runner) +
  CVE (OSV) под per-repo согласием.
- **Отклонено.** Прямое вычисление SBOM/CVE без согласия — нет (эгресс только под D6).
- **Последствия.** Пересчёт связан со снапшотом; политика пересчёта при «грязном» дереве — TODO(open) O8.

## D9. Туры

- **Контекст.** Существующий product-tour: `contracts/index.ts` (`TourDefinition`, `TourStep`,
  `TargetId`/`RouteKey`/`TriggerId`/`CapabilityId`), каталог `product-tour-catalogue.ts` (25 туров),
  рантайм `ProductTourProvider.tsx`, `routes.ts`, `ui/SpotlightOverlay.tsx`, персистентность прогонов в
  IndexedDB.
- **Выбрано.** Расширяем существующий product-tour: **динамические** `TourDefinition`, генерируемые из
  артефактов репо (статика каталога остаётся для обучающих туров приложения); новые
  `TargetId`/`RouteKey`/`TriggerId`/`CapabilityId` для поверхностей dev space; прогресс «шаг N из M»;
  персистентность прогонов — существующая.
- **Отклонено.** Новый движок туров — не строим.
- **Последствия.** Новые `TourDefinition` должны попадать в динамический источник каталога; цели
  регистрируются `useTourTarget`; сигналы «verified» не могут приходить из `ui-observation` (гвард в core).

## D10. Демо-режим (визуал туров)

- **Контекст.** Существующий spotlight-механизм (`SpotlightOverlay.tsx`, SVG even-odd маска @0.4);
  токены motion и `prefers-reduced-motion`.
- **Выбрано.** Краевой слой: тёмная радиальная виньетка по периметру окна (непрозрачность 0.10–0.18) с
  анимацией «дыхание» 4–6 с; пульс границы целевого блока; существующий spotlight-механизм сохраняется;
  прогресс-полоса и «шаг N/M»; кнопки пауза/выход. При `prefers-reduced-motion` — статичный градиент
  без пульса.
- **Отклонено.** Пульс при `prefers-reduced-motion` — недопустим; отказ от spotlight — не требуется.
- **Последствия.** Новый краевой слой поверх существующего overlay; reduced-motion гасит анимацию.

## D11. Свой вопрос

- **Контекст.** Стандартный композер ROX (`ChatPage.tsx` → `ChatDisplay.tsx`; композер
  `input/{ChatInputZone,InputContainer,FreeFormInput,CompactModelSelector}.tsx`; пикер модели
  `useSessionModelCatalog.ts`), сессии и инструменты уже есть.
- **Выбрано.** Под колонками блоков — стандартный композер ROX (пикер модели/коннекта, вложения).
  Запрос уходит в **обычную сессию, привязанную к репо** (видна в списке сессий, продолжается,
  инструменты доступны). Ответы могут содержать кнопку «Показать на экранах» → запуск сгенерированного тура.
- **Отклонено.** Отдельный чат-движок — не строим; используем существующий композер и сессии.
- **Последствия.** Связь ответов с турами (D9); сессия привязана к репо-контексту.

## D12. Playbooks: объём и перенос

- **Контекст.** Референс — SurfSense/NotebookLM; существующие примитивы: source-index (FTS5,
  `source-index.ts`), docs block-tree (`content:*`), voice-слой, агентские сессии. Лицензия SurfSense
  неоднозначна (GitHub: «Other»). Имя «Плейбуки» коллидирует со старым ярлыком SessionWorkbench
  «playbook holes».
- **Выбрано.** v1 = режим **знаний** (источники, пресет-вопросы, подкаст); затем **кодбук**. Перенос
  SurfSense — **порт концепций** на наши примитивы (source-index FTS5, docs block-tree, voice-слой,
  агентские сессии); Kokoro — опциональный новый `TtsEngine` за существующей абстракцией. Имя
  «Плейбуки» занимаем как название поверхности.
- **Отклонено.** Вендоринг SurfSense как сайдкар-сервиса и форк кода — второй стек, вес, неоднозначная
  лицензия. Коллизия имени — старый видимый ярлык SessionWorkbench «playbook holes» переименовываем в
  «Веера задач».
- **Последствия.** Playbooks строятся на существующих примитивах, не на SiYuan-поверхности (жёстко
  выключена, `KnowledgeSurfacePage.tsx`: `knowledgeEnabled=false`).

## D13. Подкаст v1

- **Контекст.** Есть TTS-движки `system`/`edge` (`TtsEngine='system'|'edge'`; `system-tts.ts`,
  `edge-tts.ts`), voice job-machine, плеер `message-tts.ts`. Мультиспикерного аудио/миксдауна нет.
- **Выбрано.** Двухголосый диалог (ведущий + эксперт) с редактируемыми шаблонными ролями
  (ярлыки/промпты); сценарий — LLM; озвучка — существующие TTS (`edge`, `system`), сегменты → сборка в
  один файл (ffmpeg), встроенный плеер + экспорт `mp3`/`srt`.
- **Отклонено.** N агентов с произвольными ролями — v1.x (голоса из фиксированного реестра).
- **Последствия.** Net-new пайплайн сегменты→ffmpeg→файл; Kokoro — опциональный третий `TtsEngine`
  (offline), включать в v1 или v1.x — TODO(open) O5; обязательность `srt` — O6.

## D14. Волны, платформы, процесс

- **Контекст.** Обязательные гейты PR: `validate:ci`, `typecheck:all`, ui-lint-ratchet,
  `product-tour-native.yml` (macos-15/windows-2025), unified-gates, `rx:validate`; i18n 12 локалей.
- **Выбрано.** Волны (одна волна = один PR): **В1** роль+флаги+пространство+клонирование; **В2** шесть
  инструментов/артефакты+рендер-поверхности; **В3** блоки вопросов + туры/демо-режим + свой вопрос;
  **В4** Playbooks-Знания (источники/пресет-вопросы/подкаст); **В5** Кодбук. Native-приёмка macOS+Windows
  (существующие гейты). Процесс: пак в `docs/specs/<date>-<slug>/`, RX-ids (резерв при старте В1),
  i18n 12 локалей (parity/sorted/coverage), зелёные `validate:ci`, `typecheck:all`, ui-lint-ratchet,
  `product-tour-native` для затронутых волн.
- **Отклонено.** webui — вне v1. Приёмка на Linux — не планируется (Linux = NOT_RUN).
- **Последствия.** Жёсткая привязка «волна = PR = гейты»; RX-ids резервируются при старте В1.
