# PRD — единые таблицы ROX

**Дата:** 30.09.2026 · **Epic:** [#1295](https://github.com/rox-one/rox-one/issues/1295) · **Статус:** требования опубликованы, первый core-срез отделён от дальнейшей реализации.

## 1. Продуктовый результат

Таблица в ROX — управляемый набор данных с типами полей, представлениями, правами, связями, журналом изменений и автоматизациями. Она не становится другим продуктом при вставке в заметку. Пользователь создаёт таблицу отдельной страницей, через команду в Note или внутри Doc; во всех случаях получает одну и ту же систему возможностей. Один набор данных можно открыть одновременно в таблице, документе, графике, форме и приложении, не синхронизируя независимые копии.

Главная проверка результата: создать таблицу в Note, изменить запись на отдельном экране и открыть её в Doc на втором клиенте после перезапуска. Идентификаторы Base/Table/View/Row/Field и значения должны совпасть. Уровень доступных действий определяется правами, поддержкой источника и подключёнными сервисами, а не местом вставки.

## 2. Границы и решения

Выбран нативный путь развития ROX Bases поверх существующих Pages, Notes, Tiptap, native entity owners, command registry и automation runtime. Baserow используется как функциональный референс. Встраивание отдельного сервера Baserow через iframe/API не выбрано: оно не решает требование общего владения данными, прав и команд ROX. Обычная HTML/Markdown-таблица также не решает требования типизированных строк и автоматизации; она сохраняется как явно простой формат для старых документов и экспорта.

Это не проект spreadsheet-движка с адресами A1 и workbook-формулами: такой объём относится к #1092. Это не новый редактор документов, каталог файлов, почтовый клиент или независимый планировщик. Не копируем коммерческие ограничения, бренд, изображения и исходники референса. Любое будущее заимствование кода требует отдельного path/SHA/license review.

Новая slash-команда «Таблица» создаёт управляемую таблицу по умолчанию. «Простая Markdown-таблица» остаётся отдельным осознанным выбором, чтобы не ломать переносимость. Существующие простые таблицы не конвертируются автоматически при открытии файла.

## 3. Пользователи и права

Владелец рабочего пространства управляет политиками и публикацией. Автор таблицы задаёт schema и представления в пределах делегированных полномочий. Редактор изменяет разрешённые строки и поля. Читатель не получает права записи из-за видимости кнопки. Сервисный агент имеет отдельную identity и ограниченный контекст. Внешний пользователь формы может иметь право отправки, не имея права чтения базы.

Доступ к Doc/Note не даёт доступа к вложенной таблице. Доступ к таблице не даёт автоматического доступа к relation target, вложению, закрытому полю или внешнему API. При отказе показываем безопасное состояние без stale заголовка и без данных, сохранившихся от предыдущего пользователя.

## 4. Что получает каждая новая таблица

Один schema registry и редакторы полей; default Grid view; фильтры, сортировку, группировку, поиск и набор доступных дополнительных представлений. У таблицы есть адресуемый источник, карточка строки, история, настройки доступа, точки вызова автоматизаций, возможность построить график или форму и открыть общую таблицу из embed. Доступные средства не обязаны быть сразу настроены: Button без зарегистрированного действия остаётся конфигурацией, отправка email требует подключения, AI требует разрешённой модели, sync требует источника.

| Уровень | Требования |
|---|---|
| Данные | Stable IDs; типы Title/Text/Number/Select/Multiselect/Checkbox/Date/URL/Email/Phone/Status/Formula/Relation/Lookup/Rollup/Image/Audio/Video из #1239; Button — отдельное расширение #1299; дополнительные типы только через общий registry |
| Представления | Grid, существующие List/Board/Gallery/Calendar/Timeline пакеты, Chart/Form; общие и личные views, saved filters и сортировка; layout не меняет source |
| Редактирование | Typed validation, keyboard/IME, многоклеточная вставка с preview, optimistic draft до durable receipt, conflict/retry без потери ввода |
| Связи | Canonical native refs, lookup/rollup с независимыми правами, ссылки на Notes/Tasks/Docs/Meetings/Calendar и файлы через adapters |
| Действия | Row Button, workflows, HTTP/email/Slack/OpenURL через существующие безопасные диспетчеры; ordered outputs и история |
| Управление | Row/field policies, agents, аудит, schema migration, import/export, синхронизация, публикация и настраиваемые квоты |

## 6. Основные пользовательские маршруты

### Создать, вставить, открыть

В Workspace нажать «Новая таблица», либо вызвать slash-команду в Note/Doc. Выбрать пустую таблицу, шаблон или существующий native источник. Указать название и минимальную schema. Сервис создаёт Base и Grid, затем прикрепляет ссылку в host. До подтверждения сохранения показывается draft/pending; после него можно открыть источник полностью. Повторное нажатие не создаёт второй dataset. Если attaching документа конфликтует, уже созданная таблица доступна для восстановления, а не молча удаляется.

### Изменить данные и представление

Редактор меняет типизированное значение. Ошибка формата остаётся в ячейке с объяснением. Конфликт показывает собственный draft и текущую revision; новый запрос не перетирает чужую правку. Фильтр и сортировка могут быть личными; shared view меняется отдельной командой. Встроенный режим сохраняет те же действия, но компактную панель. Expand ведёт к тому же Base/View; Escape возвращает фокус на исходный block.

### Продвинуть простую таблицу

Выбрать существующую Markdown-таблицу → «Сделать управляемой» → проверить предлагаемые типы, именование и потери → подтвердить. Сохраняется original source revision и loss report. Конвертация защищена source span hash и host CAS. Обратное представление в Markdown — snapshot export; живые действия и связи не маскируются как полностью переносимые.

### Настроить кнопку

Добавить поле Button → label → выбрать зарегистрированные действия → связать входы с row.fieldId и предыдущими outputs → preview → publish. На строке запуск проверяет актуальные права и revisions. Показываются pending/run history/partial failure. Пример «HTTP → создать строку → email» принимается только с проверяемой передачей данных и реальными receipts. Preview не отправляет запросов и писем.

### Обработать письмо или sync

В существующем automation builder выбрать Email trigger, подключить готовый incoming gateway и создать адрес. Тестовый trigger получает синтетическое письмо, затем после проверки публикуется production version. Повторная доставка не дублирует запись. Для Sync таблица хранит binding, а history — durable job с checkpoint; stale показывается отдельно от live.

### Собрать приложение или dashboard

Добавить Graph/Table/KPI на существующую Page, выбрать источник и query. Изменение layout сохраняется отдельно от данных. Публикация задаёт поля, действия и guest policy. Видимость родительской страницы не делает весь Base публичным. Формы используют существующий механизм #1095/#1290 и создают canonical записи, а не отдельную базу ответов.

## 7. UX и качество взаимодействия

Сохраняем компактную оболочку и привычную навигацию. Для таблицы — плотная сетка и contextual toolbar; для документа — встроенный блок; для dashboard — свободная композиция. Не заменяем все экраны одинаковой сеткой карточек. Используем текущую тему, русский интерфейс через t() и ключи всех локалей репозитория.

Нужны состояния loading, source-empty, filtered-empty, offline/stale, denied, read-only, validation, conflict, unsupported и missingDependency. Ошибка не обозначается только цветом. Длинное действие имеет историю и возможность отмены, а не бесконечный spinner. У каждой недоступной кнопки есть причина. Hover показывает справку, но не запускает действие и не расширяет контекст агента. Keyboard, IME, screen-reader labels, возврат фокуса, reduced motion и масштаб 200% — обязательная приёмка.

## 8. Измеримые критерии успеха

Функциональное покрытие: 14/14 групп R1 имеют задачи и проверочные сценарии; готовность означает исполнение, а не наличие ссылки на issue. Для трёх origins одинаковы identity и набор поддержанных capability paths. Ноль повторных внешних эффектов в replay/crash тестах; ноль утечек в ACL/derived-cache тестах; ноль потерь исходных данных в promotion/schema migration fixtures.

Предлагаемые performance budgets для зафиксированного CI hardware: 10k rows × 30 fields; p95 первого cached grid <500 ms, страницы server query <1000 ms; отдельная 100k-record server fixture, 1000-cell paste и 10 concurrent editors. Это целевые требования, не уже измеренная производительность. Перед обещанием SLA фиксируются оборудование, dataset, сеть, baseline и стоимость индексации.

## 9. Выпуск и текущий объём

Сначала принимаются owner/persistence/query/ACL, затем общий grid+embeds+creation, затем богатые поля, automation и интеграции, затем публикация и сквозная приёмка. Feature availability остаётся disabled/missingDependency до реального подключения соответствующей службы. Полный epic не закрывается по результатам unit tests codec.

Текущий PR начинает только #1296: reference-only codec, identity helpers, fail-closed availability metadata и тесты. Он не создаёт сохраняемые пользовательские строки, не включает новый редактор, не принимает почту и не выполняет workflows. Полный прогресс проверяется в [VERIFICATION](VERIFICATION.md), дальнейшее исполнение — в [плане](../superpowers/plans/2026-09-30-unified-tables.md).
