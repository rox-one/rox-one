## 1. Результат для пользователя

ROX поставляется с готовой командой агентов. Пользователь начинает встречу, разрешает нужный захват и работает без самостоятельной сборки промптов, установки MCP-серверов или подписок на Cluely, Tana, Supernormal и Fireflies. Агенты помогают во время разговора, сохраняют контекст, предлагают изменения и выполняют разрешённую работу. Результаты доступны в обычных Notes, Tasks, Projects, Calendar, Files и сессиях ROX.

Основная история: «Обсудили → поняли → согласовали → выполнили → проверили». Успех — сохранённая и проверенная работа, а не красивый протокол и не количество запущенных агентов.

Conation интегрируется через данные, доменные функции, события и адаптеры; собственный UI ROX обязателен. Ссылка, iframe, тип TypeScript, заглушка или тестовый ответ не являются интеграцией. Исходный `agisota/conation` на дату проверки недоступен подключению GitHub (404). Полный перенос upstream нельзя объявить завершённым до закрытия #333 с исходниками/версией/схемой/лицензиями. Это не блокирует нативный сценарий ROX.

## 2. Аудит и продуктовые ориентиры

Подробные первоисточники и границы проверенного находятся в SOURCE-AUDIT. Возможности референсов — заявления производителей, не результаты нашего сравнительного теста.

- Cluely: контекст разговора и выбранного экрана, ответы в момент звонка, горячая клавиша и плавающее окно. Не переносим обещание универсальной невидимости.
- Tana: выполнение работы во время встречи, общая память и повторяющиеся агентные процессы. Собственные комнаты и захват сторонних звонков — разные способы входа, не одна функция.
- Supernormal: создание материалов, задачи и изменения в Linear из контекста встречи.
- Fireflies: живые заметки/транскрипт, поручения, ручные заметки, поиск по разговорам, клипы, помощь и интеграции.

«Все функции» означает версионированный реестр пользовательских возможностей с проверяемой приёмкой. Нельзя заявлять бессрочный 100% паритет с меняющимся каталогом чужого продукта. Новая подтверждённая функция добавляется в реестр с владельцем и тестом; исключение требует явного решения владельца продукта, а не молчаливого удаления строки.

## 3. Пользователи и ценность

Инициатор/руководитель получает меньше ручного переноса договорённостей. Исполнитель получает конкретное поручение с происхождением и сроком. Продажи/консалтинг получают контекст клиента, подготовленные материалы и последующие действия. Команда получает доступную по правам память решений, а не личные изолированные чаты. Администратор получает управление доступом, обработкой данных, расходами и журналом действий.

Не требуется выдавать всем участникам полный доступ к проекту ради участия во встрече. Личные заметки и общекомандные результаты имеют разные аудитории.

## 4. Поставка и восемь системных ролей

| ID определения | Роль | Триггер | Результат |
|---|---|---|---|
| `rox.meeting.coordinator` | Координатор | подготовка, начало, завершение | справка, повестка, распределение заданий, итог покрытия |
| `rox.meeting.assist` | Помощник | явный вопрос/горячая клавиша | ответ с источниками, пояснение экрана, уточняющий вопрос |
| `rox.meeting.scribe` | Секретарь | разрешённый поток речи | транскрипт, заметки, решения, вопросы, поручения |
| `rox.meeting.knowledge` | Хранитель знаний | новый факт/решение | предложение изменения знаний с diff и происхождением |
| `rox.meeting.executor` | Исполнитель | подтверждённая команда | реальное действие, receipt, readback, видимый статус |
| `rox.meeting.author` | Автор материалов | запрос документа/исследования | версионированный артефакт с проверкой формата |
| `rox.meeting.followup` | Контролёр | завершение/разрешённое расписание | проверка обещаний, подготовленные напоминания |
| `rox.meeting.analyst` | Аналитик | профиль встречи/периодический обзор | риски, требования, клиентский контекст, предложения CRM |

Это восемь версионированных ролей поверх существующего runtime, а не восемь обязательных постоянно работающих процессов. Один вход ROX маршрутизирует задания. Поставляемый пакет содержит определения, навыки, схемы результатов, политики, модельные роли, шаблоны встреч и сценарии проверки.

`installed`, `enabled`, `authorized`, `healthy`, `running` независимы. По умолчанию определения установлены и доступны в UI; лёгкое нативное редактирование работает без внешних сервисов. Захват не начинается без разрешения, отправка не происходит только из-за `enabled=true`, локальные веса не считаются установленными по наличию их названия. Изменения пользователя и отключение роли переживают обновление. Нельзя расширять права при обновлении пакета без нового разрешения.

## 6. Сквозные истории

S1 — чистая установка: увидеть восемь ролей, отказаться от микрофона, продолжить работу с Notes, позднее разрешить запись и получить первый результат.
S2 — разговор в Zoom/Meet/Teams: live transcript → «Иван, подготовь прототип к пятнице» → предложение → подтвердить → нативная Task со ссылкой на фрагмент. После перезапуска задача та же.
S3 — «не делаем прототип; сначала исследование»: отрицание не создаёт задачу; исправление снимает устаревшее предложение; подтверждённая ранее операция требует нового корректирующего действия.
S4 — клиентский звонок: справка → помощь → документ → предложения CRM и письма → проверенное выполнение разрешённых изменений.
S5 — дизайн-обзор: выбранный экран → обсуждение → требование → спецификация → issue/draft PR; никакого shell-execution только по голосу неизвестного участника.
S6 — следующая встреча: ROX проверяет фактические изменения, различает выполненное, просроченное и неизвестное, готовит повестку.
S7 — офлайн/сбой: разрешённые данные сохраняются, интерфейс маркирует разрыв, фоновые задания восстанавливаются без дублей.
S8 — Conation недоступен: нативная работа продолжается, внешняя операция остаётся blocked/queued с причиной, без ложного success.
S9 — командный доступ: общий результат доступен разрешённым людям, частная заметка и закрытый проект не утекают.
S10 — собственная комната: отдельный проверенный медиаконтур, не кнопка-пустышка и не prerequisite S2.

## 7. Этапы продукта

M0: нативный вертикальный срез S1–S3/S7/S8. M1: помощник, знания, артефакты и интеграции S4–S6. M2: подтверждённые функции Conation и командная работа. M3: дополнительные capture providers и собственные комнаты. M0 не называется полным паритетом; M3 не требуется для начала ценности.

Целевые инженерные бюджеты, не текущие измерения: первая частичная расшифровка p95 ≤2 с на поддержанном streaming route; предложение ≤5 с после финализации достаточного фрагмента; UI feedback ≤150 мс; финальная сводка часовой встречи ≤60 с на заявленном эталонном стенде. Более медленный маршрут маркируется degraded/batch. Эти цели проверяются в I030; невыполнение нельзя скрыть заменой стенда.

Качество: на удержанном RU/EN корпусе целевая точность извлечения поручений ≥95%, полнота ≥85%; точность разрешённых owner/date среди неотложенных случаев ≥95%, отдельно доля abstain. Для safety-корпуса — 0 неразрешённых внешних действий и 0 утечек между workspace; это критерий набора тестов, не универсальная гарантия. Для ссылок — 100% записанных извлечений имеют валидный источник либо явное происхождение manual.

Ценность: медианное время от окончания договорённости до подтверждённой задачи; доля принятых предложений; доля задач с проверенным результатом; время ручного исправления; количество дублей; стоимость на минуту и принятый результат. Не оптимизировать количество предложений ценой false positives.

## 8. Границы безопасности и эксплуатации

Системный набор доступен по умолчанию, но mic/screen/cloud-send и внешние операции требуют соответствующих grants. `allow-all` не обходится и не переопределяется глобально: поверх него действует capability-policy meeting agents. Текст встречи/документа — недоверенные данные, не источник новых полномочий. Предложения по умолчанию не отправляют письма и не изменяют внешние проекты без разрешения. Пользователь может разрешить ограниченный класс действий один раз с scope, expiry и budget.

Срок хранения выбирается явно до durable записи; обработка в памяти и архивирование — разные режимы. Отключение облачного распознавания не означает запрета локальной обработки, а отсутствие локальных весов не даёт разрешения отправить аудио в облако. Бюджет бесплатного default route предоставляет сервер; отсутствие квоты — объяснимое состояние, не бесконечный retry и не обещание безлимита.

## 9. Определение завершённости

Документы готовы, когда требования, задачи, зависимости, тесты и источники связаны и прочитаны обратно из GitHub. Реализация готова только после реальных операций через UI→RPC→storage/provider→readback на свежем SHA, RED/GREEN тестов, отрицательных сценариев, перезапуска и проверки упакованного приложения. Fixture, source-string assertions, экспорт TypeScript-типа и HTTP 202 не подтверждают готовую продуктовую функцию.
